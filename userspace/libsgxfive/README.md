# libsgxfive and sgxfive-test

A small C11 library over the **sgxfive** render-node ioctls (`kernel/uapi/sgxfive_drm.h`,
designed in `design/sgx545_render_uapi.md`), a test tool that redoes the debugfs checks of the
bring-up from userspace, and an in-process mock of the kernel side so all of it is tested
without the hardware.

This is a development tool. It is not the open-source userspace that upstreaming the UAPI
needs (that is a Mesa driver, design §1.3–§1.4).

## Layout

| path | what |
|------|------|
| `include/sgxfive.h` | device, DEV_QUERY, BOs, VM contexts, contexts, syncobjs, SUBMIT_JOBS |
| `include/sgxfive_xfer.h` | transfer builders, the program-source interface, the transfer engine |
| `include/sgxfive_render.h` | render jobs: triangle scene builders, CPU reference, render engine |
| `include/sgxfive_mock.h` | the mock render node |
| `src/dev.c` | ioctl wrappers and the OS backend (`open`/`ioctl`/`mmap`) |
| `src/xfer.c` | pure builders: DOUTU, PBE state, background objects, texture words, registers |
| `src/xfer_job.c` | the engine: places programs in the client VM, fills and copies |
| `src/prog_asm.c` | the assembled program source: our own programs (default) |
| `src/prog_asm_gen.h` | its tables, generated by `tools/gen_progs.py` (`make gen`); checked in |
| `src/prog_fake.c` | test-double program source (mock only) |
| `src/render.c` | the triangle's programs, MTE state, VDM stream and geometry at a VM's addresses |
| `src/tri_progs_gen.h` | its programs, generated by `kernel/gen_tri_progs.py --user`; checked in |
| `src/mock.c` | the mock: kernel rules plus tiny transfer and render interpreters |
| `tools/sgxfive-test.c` | the CLI |
| `tools/gen_progs.py` | assembles `tools/usse-asm/progs/` into `src/prog_asm_gen.h` |
| `tests/` | C tests (TAP), `prog_dump.c` (a harness), `test_cli.py`, `test_prog_asm.py` |
| `third_party/` | Linux's `drm.h`/`drm_mode.h` (MIT) and non-Linux shims; see its README |

## Build and test

```sh
make            # build/libsgxfive.a, build/sgxfive-test
make check      # C unit tests, then pytest on the CLI and the programs, against the mock
make check CC='cc -m32'   # the same on i686 (layout test included)
make gen        # regenerate src/prog_asm_gen.h after editing tools/usse-asm/progs/
```

No dependencies beyond a C11 compiler and, for the pytest tests, Python with pytest (the
repo's `.venv/bin/pytest` if present, else `pytest`; override with `PYTEST=`) and a host
`cc` for `tools/usse-asm`, which `test_prog_asm.py` and `make gen` run. libdrm is not used: the
library calls the ioctls directly with the UAPI header. It builds and passes on macOS, Linux
x86-64 and Linux i686.

Tests are written first. The C tests are plain programs printing TAP (`tests/tap.h`):

- `test_uapi` — every UAPI struct is the sum of its members (no implicit padding, so i686 and
  x86-64 agree), sizes and offsets, the transfer command at the `sHWRegs` offsets, flag masks;
- `test_xfer` — the pure builders against the worked examples of `design/sgx545_transfer.md`
  (§4.2.3–§4.2.7, §4.4.2–§4.4.5): DOUTU words, PBE state, background objects, the truncated
  texture coordinates, T0–T3, the register block, the `USSE_LIMM` split;
- `test_dev` — the wrappers against the mock: discovery by driver name, DEV_QUERY size rules,
  BO flags, VM_MAP heap and overlap rules, contexts, syncobjs (binary and timeline), and the
  SUBMIT_JOBS validation rules including the reserved update list;
- `test_job` — fills and copies through the engine, once with each program source: with the
  harness layout the programs equal the debugfs recipes word for word; every destination
  dword is checked (the rectangle matrix of the hardware runs); isolation between VMs,
  faults, lost contexts, read-only maps; the errors failed jobs' fences carry (`-EIO` for
  the job that faulted, `-ECANCELED` for its context's jobs behind it, none for another
  context's) and the waits that report them;
- `test_prog` — the assembled source: its metadata equals the fake's, every word the fake
  writes is the same over random placements, the bodies the fake leaves zero are present,
  and an unplaced or unreachable `DOUTU` target fails;
- `test_render` — the render builders at the debugfs test's addresses produce the words the
  kernel's `sgx_tri.c` does (its KUnit values, which the laptop ran), and other sizes move
  exactly the size-dependent words; `sgxfive_tiling()` against the closed driver's layouts;
  the CPU reference and the pixel checker;
- `test_render_job` — render contexts and jobs against the mock: DEV_QUERY, the kernel's
  rules on contexts, commands and the reserved render heaps, the triangle at several sizes
  every pixel checked, contexts that state their largest target (bounds, targets within it
  rendered, larger ones refused), a faulting render losing its context and its wait
  reporting `-EIO`, transfers keeping
  `PDS_EXEC_BASE` at the PDS heap base, transfers and renders interleaved.

`tests/test_cli.py` drives `sgxfive-test --mock` through every subcommand.
`tests/test_prog_asm.py` checks that `src/prog_asm_gen.h` is what `gen_progs.py` writes
today, and runs `build/prog_dump` against `tools/fwcutter/fwload.py`'s `build_tq()`: the
recipe placements and 100 random placements and parameter sets on a firmware built from our
source alone, and, with the user's `libsrv_init.so` and `libsrv_um.so`, 50 more on the cut
file. Every byte must match.

## The mock

`sgxfive_mock_create()` returns an object whose `struct sgxfive_backend` replaces `open`,
`close`, `ioctl`, `mmap` and `munmap`; every library function takes a backend
(`sgxfive_dev_open(be, ...)`, NULL meaning the real one), so the code under test is the code
that will run on the laptop. The mock implements what the kernel side must:

- render nodes: optionally another driver on `renderD128` (discovery must skip it);
- DEV_QUERY with the `pvr` size rules, and the heap table of the `REV1` layout (default; quirk
  `SAMPLE_CACHE`, bridge revision 3) or of the debugfs harness layout (`--mock=harness`);
- GEM BOs with mmap only when `ALLOW_CPU_ACCESS`; zeroed padding and flag masks everywhere;
- VM contexts with per-mapping read-only flags, mappings only inside one user heap, `-EEXIST`
  on overlap, whole-mapping unmap; BOs live while mapped; closing the file frees everything;
- transfer and render contexts (a render context states its largest target, 1 to 4096 each
  way, a transfer context none; 32 render contexts per VM; none in the harness layout, which
  has no room for the reserved render heaps), DRM syncobjs (`CREATE`, `DESTROY`, `WAIT`,
  `TIMELINE_WAIT`, and `HANDLE_TO_FD` with `EXPORT_SYNC_FILE`, whose sync_file answers
  `SYNC_IOC_FILE_INFO` with the fence's status);
- SUBMIT_JOBS: all jobs validated before any runs, the failing index in `jobs.count`, the
  §4.5 and §11.4 checks (job and context types match, `PDS_EXEC_BASE` of transfers at the PDS
  heap base, render targets within their context's maximum with the tiling words of their
  size), the update list rejected while `max_updates` is 0, waits needing a fence (as
  `drm_syncobj_find_fence`) unless an earlier job of the same call signals it.

Jobs run synchronously. A transfer is executed by an interpreter that follows the job's own
pointers through its VM: pixel-event PDS → EOT program → PBE state; background object → PDS
primary → shader (fill colour) or texture words (copy); the vertices and the render box clip
the rectangle. So a wrong address, encoding or placement shows as wrong pixels or a fault (a
mutation of any builder fails `test_job`). A render is executed the same way, for the scenes
our builders make: the VDM stream's state blocks (the pixel primary's fill colour, the
viewport) and triangle index lists through their vertex PDS program, the background object's
colour, and the PBE state of the end-of-tile program; each pixel of the target gets the last
triangle covering its centre, or the background. A fault writes nothing, counts in the stats
and loses the context, as with the kernel's recovery: the job's fence signals with `-EIO`,
later jobs of the context in the same call with `-ECANCELED`, and later submissions get
`-ECANCELED`. A fill shader whose colour instruction is not a limm `mov` is a program the
interpreter does not know, which it treats as a hang (a fault).

What the mock cannot tell: whether the real firmware and hardware accept the programs and
registers. That is what the laptop runs are for.

## Library API in brief

```c
sgxfive_dev_open(be, path_or_NULL, &dev);       /* scans renderD128..191 for "sgxfive" */
sgxfive_dev_info(dev);                          /* GPU, FW, job limits, runtime, heaps */
sgxfive_bo_create(dev, size, flags, &bo); sgxfive_bo_mmap(bo, &p); sgxfive_bo_destroy(bo);
sgxfive_vm_create(dev, &vm); sgxfive_vm_alloc(vm, heap, size, align, &addr);
sgxfive_vm_map(vm, addr, bo, offset, size, flags); sgxfive_vm_unmap(vm, addr, size);
sgxfive_ctx_create(vm, &ctx); sgxfive_ctx_destroy(dev, ctx);  /* a transfer context */
sgxfive_render_ctx_create(vm, max_width, max_height, &ctx); /* targets up to that size */
sgxfive_syncobj_create(dev, signaled, &h); sgxfive_syncobj_wait(dev, h, point, timeout_ns);
sgxfive_syncobj_wait_job(dev, h, point, timeout_ns, &job_error);
sgxfive_syncobj_fence_status(dev, h, &status);  /* 1, 0, or the fence's error */
sgxfive_submit(dev, jobs, n, &failed); sgxfive_submit_transfer(dev, ctx, flags, cmd, w, s);

sgxfive_xfer_create(vm, ctx, program_source, &x);
sgxfive_xfer_fill(x, &dst, &rect, colour, signal);
sgxfive_xfer_copy(x, &src, sx, sy, &dst, &rect, signal);
sgxfive_xfer_wait(x, timeout_ns);
```

Functions return 0 or a negative errno.

### Job errors

A job that faults or hangs is recovered by the kernel and fails: its fence signals with an
error (`-EIO` for a fault, `-ETIMEDOUT` for a hang without one, `-ECANCELED` for jobs of the
lost context queued behind it; design §4.7, render_uapi R15). DRM's syncobj wait succeeds all
the same, so the waits read the fence's status from a sync_file exported from the syncobj
(`SYNC_IOC_FILE_INFO`) and return that error: `sgxfive_syncobj_wait()` for a binary syncobj,
`sgxfive_xfer_wait()` and `sgxfive_render_wait()` once for the engine's last job.
`sgxfive_syncobj_wait_job()` returns the wait's result and the job's error apart. A signalled
timeline point carries no error (the kernel's chain fences drop it), so waits on points report
only the wait.

### Program sources

The kernel builds no GPU programs: userspace places them in its own VM (design §4.4). The
engine takes them from a `struct sgxfive_prog_source`, two callbacks over the ids, metadata
and parameters of the firmware file's transfer-queue templates (`design/sgx545_fw_format.md`
§9, §10):

- `meta(id)` → heap, temporaries, attributes, size, alignment, PDS data size;
- `build(id, env)` → the finished image, given the parameters (colour, PBE words, texture
  words) and where everything was placed (addresses and DOUTU words of the USE programs).

The engine places the seven programs of a fill or copy in a private three-page BO mapped into
the context's VM (PDS_PIXEL, USSE_PIXEL and GENERAL pages, 16-byte slots, which reproduces the
debugfs recipes), computes the DOUTU words, builds the background object and the register
block, and submits. One job is in flight per engine.

Two sources exist:

- `sgxfive_prog_asm_create()`, the default: our own programs from `tools/usse-asm/progs/`.
  They assemble bit for bit to the closed templates, so their images run on hardware, and
  the library needs no file and no closed input. `build` is `fwload.build_tq()` for one
  program: copy the template, apply its `TQ_PATCHES` records in order (format §9.4).
- `sgxfive_prog_fake_create()`, a test double that writes the words the design documents
  print and leaves the closed bodies it does not know (USE secondary, pixel-event PDS code)
  zero. Its images must never reach a GPU: the CLI refuses `--programs=fake` without
  `--mock`.

The assembled programs are generated into C, not assembled at build time. `src/prog_asm_gen.h`
holds the words, each commented with its instruction, and the `TQ_META` and `TQ_PATCHES`
records of `tools/fwcutter/facts.py`; it is checked in and `test_prog_asm.py` fails when it
is stale. That keeps the library a plain C11 build: cross and `-m32` builds need no host
assembler, Python or build-time tool, and the generated words are reviewable in a diff. These
are our programs, so the tables may live in the tree; no closed byte is stored. A source
reading the user's `.fw` would be a thin adapter of the same interface but is not needed.

## sgxfive-test

```
sgxfive-test [--mock[=rev1|harness|none]] [--device PATH] [--programs=asm|fake]
             <command> [options]

query                          GPU, firmware, job limits and heaps
dummy [-n N]                   N dummy transfers chained through one syncobj
fill  [--width W --height H --x X --y Y --stride S --colour C]
copy  [--width W --height H --sx X --sy Y --src-stride S --dx X --dy Y --dst-stride S]
isolation                      kernel-heap-unmappable, same-address-separate-vms,
                               other-vm-address-faults, fault-recovered-quickly,
                               lost-context-cancelled, other-context-survives,
                               queued-innocent-job-reruns, read-only-faults,
                               faulting-file-banned
tri [--width W --height H -n N] [--max-width W --max-height H] [--fault]
                               the first triangle on a render context, N renders in
                               alternating colours, every pixel against the CPU reference
                               and the area after the target against a sentinel; the
                               context takes targets up to --max-width x --max-height
                               (default: the target's size); --fault unmaps the scene's
                               stream page first, so the render faults and fails
contexts [--width W --height H -n N]
                               N render contexts (default 32) for targets up to W x H
                               (default 64 x 64) in one VM, and the MemFree and LowFree
                               they cost (/proc/meminfo)
q4                             probe Q4: client fill shaders that read and write SGX
                               registers, read unwritten temporaries, kick code base 15;
                               prints what reached memory (no pass/fail)
probe [--temps N] FILE...      each FILE, a USSE program assembled by tools/usse-asm, runs
                               as the shader of its own 64x32 fill with N temporaries
                               (default 32, at most 128); prints o0 ("o0 0x... (2048 of
                               2048)", or "mixed" with the values) or "failed: ...", and
                               the dwords of a 64 KiB scratch buffer the program changed
```

`probe` runs the hardware probes of `tools/usse-asm/probe.py` (table and programs in
`tools/usse-asm/progs/probes/`): a probe presets its inputs, runs the instruction under test
and writes the result to `o0`. When the pixels differ, the four most frequent values are
printed. A `mov d, #0x5CAFnnnn` (a limm) is patched to load the scratch buffer's address +
`nnnn`; the buffer starts with dword `i` = `0xD0000000 | i`, so loads see which dword they
read and stores show up as changed dwords. `--mock` takes the colour from the program's second
instruction, as for fills, and treats any other second instruction as a hang.

A job that faults or hangs is reported with its error and the lost context, as the wait
returns it: `probe NAME: failed: job faulted, context lost (Input/output error)` (`job hung`
for `-ETIMEDOUT`, `job cancelled` for `-ECANCELED`); `q4` prints `NAME: job failed: ...` and
`tri` exits 1 with `sgxfive-test: render: job faulted, context lost (...)`. A probe whose job
completes without writing a pixel prints `failed: no pixel written`. `isolation` checks that
each faulting fill's wait returns `-EIO` and the re-run innocent job's returns 0.

Exit status 0 when every check passes, 1 on a failed check or call, 2 on usage errors. Each
subcommand mirrors a debugfs file of the bring-up: `dummy` ↔ `xfer_dummy`/`xfer_sync`, `fill` ↔
`xfer_fill` (sentinel-filled destination plus a guard page, every dword checked), `copy` ↔
`xfer_copy` (a source in which every byte varies), `isolation` ↔ `xfer_iso`, `alias_ro`,
`xfer_ro`, `tri` ↔ `tri`. `fill`, `copy`, `isolation` and `q4` print the program source
(`programs asm`).
`q4` means something only on the hardware: the mock's interpreter knows no `ldr`/`str`, so
its probes fail there as hangs.

## Against the real kernel

The same binary runs on the laptop without `--mock`, against the render node of design §8
P3–P6 and P9 (booted with `gma500_gfx.sgx_render=1`, or it finds no render node): `query`,
`dummy`, `fill`/`copy`/`isolation`/`q4` with the assembled programs, and `tri` with the
triangle's (design §11.12 has the results). The tests here also became
IGT tests (`userspace/igt/`): the program-free ones (queries, BOs, VM rules, dummy jobs,
syncobjs, the `-EINVAL` paths) with raw ioctls, as `tests/panfrost` and `tests/v3d` do, and the
fill, copy, isolation and render tests through a vendored copy of this library's engines and
assembled programs (`src/prog_asm_gen.h`, `src/tri_progs_gen.h`), since IGT cannot ship closed
bytes.
