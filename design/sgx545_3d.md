# SGX545 3D — what the GLES2 stack submits for one triangle, and our first triangle

The 3D design note. It records what the closed Cedarview GLES2 stack (DDK 1.7.862890) submits
to draw one constant-colour triangle into a 64×64 RGB565 pbuffer, as captured by the harness
(`harness/ukernel-extract/README.md`, "3D capture"), with the structures decoded by
`kick3d.py` and `summary3d.py`, and how the microkernel runs it (§12, §13). §14 is the result:
the minimal TA + 3D job built by the kernel from our own programs, which renders a triangle on
the laptop **[HW]**.

Conventions:

- Tags as in the other design documents: **[DDK]** GPL DDK source, **[CAP]** captured from the
  closed userspace under the harness, **[RE]** read from closed-binary disassembly, **[infer]**
  inference, to verify before relying on it. **[PSP2]** marks layouts and field names read
  from the DDK 1.8 client headers in `reference/PVR_PSP2` (`reference/CATALOG.md` §7): facts
  only, with every SGX545 conditional member pinned by a captured structure size.
- `CDV` is Intel's GPL Cedarview kernel patch, `DDK` the GPL `reference/sgx545-ce` tree (the
  first, verbatim commit). Device addresses are the harness layout (heap bases of
  `sgxconfig.h`, first object at heap base + `0x1000`); objects are page-aligned and never
  reused, so addresses are stable between runs but not those of a real driver.
- "obj N" is the harness object index in the capture (`extracted/gles2_tri/MANIFEST.md`).

## 1. How it was captured

The closed stack ran on the build host as i686 code under `fakedrm.so` (an `LD_PRELOAD`
libdrm). Nothing in the stack needed patching **[CAP]**:

- **Window system.** libIMGegl loads the WSEGL module named by the `WindowSystem` app hint
  from `/etc/powervr.ini` (default `libpvrPVR2D_DRIWSEGL.so`) and takes its function table
  from `WSEGL_GetFunctionTablePointer`. The closed modules export interface version 2: a
  version word and 14 entry points **[RE]**. Our `fakewsegl.c` offers one RGB565 config and no
  native drawables; `eglCreatePbufferSurface` never calls into it, so a pbuffer needs no
  display, no libpvr2d and no display-class device.
- **Kernel answers.** The client path needs the heap list (11 heaps including SYNCINFO
  `0xE0000000` and the per-context parameter heap `0xC0000000`), allocations with sync objects,
  `SGX_GETCLIENTINFO` (the `asInitDevData` srvinit gave the kernel), `SGX_GETMISCINFO`
  `DRIVER_SGXREV` (DDK version `0x010711`, build 862890, build options `0x60218`; with
  zeros `eglInitialize` fails with `EGL_BAD_ALLOC`), the global event object, the host
  control block, and the HW render and transfer context registrations.
- **ABI details pinned by the run.** `ALLOC_DEVICEMEM`'s OUT is 19 dwords: `sCpuPAddr` is
  32-bit, the sync info is the last five dwords, and the client maps a buffer by passing its
  **kernel** handle (`hKernelMemInfo`, `hKernelSyncInfo`) to `MHANDLE_TO_MMAP_DATA` **[CAP]**.
  `SGX_DOKICK`'s IN is 564 bytes, which matches `SGX_CCB_KICK` with
  `SUPPORT_SGX_NEW_STATUS_VALS` on and generalised sync objects off, the CDV configuration
  **[DDK/CAP]**.
- **Kernel and EDM emulation.** At each kick the shim performs `SGXDoKickKM`'s writes to the
  client CCB (§4.2), snapshots every object, then writes the status values and bumps the sync
  complete counters as the EDM would, so `glFinish` returns.

## 2. The call sequence

- **`eglInitialize`**: connect, enumerate, `SGX_GETMISCINFO`, memory context, client info,
  misc info, global event object, internal dev info, 70 allocations, HW render and transfer
  context registration. 72 objects: PB, render context, TA CCB, and the transfer queue with
  52 small pixel-shader buffers, its built-in programs **[infer]**.
- **`eglCreatePbufferSurface`**: 40 allocations: colour buffer, three render details, RT data
  set, TADATA buffers, background object, end-of-render PDS buffer.
- **`eglCreateContext`**: 21 allocations: vertex and index buffers, VDM stream, USSE and PDS
  circular buffers, status words.
- **Shaders, `glClear`, `glDrawArrays`**: no bridge calls but two allocations in the draw.
- **`glFinish`**: two `SGX_DOKICK`s.
- **`eglTerminate`**: flush render target, 17 sync-token waits, unregister both contexts,
  free everything.

No `SGX_FINDSHAREDPBDESC` / `ADDSHAREDPBDESC`: the build uses `SUPPORT_PERCONTEXT_PB`
(CDV `Makefile`) **[DDK]**, so the client allocates its parameter buffer itself **[CAP]**.
Shader compilation is CPU-only; the programs are copied into circular buffers at draw time.

## 4. The kick

### 4.1 HW render context — `SGXMKIF_HWRENDERCONTEXT`, `0x44` [PSP2/CAP]

Registered once with `SGX_REGISTER_HW_RENDER_CONTEXT` (`SGX_CMD_BASE + 20`): the kernel copies
the client image into KERNEL_DATA and writes the page-directory address at offset 8, exactly
as for the transfer context **[DDK]**. Captured: flags `0x21` (new context, per-context PB),
priority 0, `ta_ccb_base_dev_addr` / `ta_ccb_ctl_dev_addr` (the TA client CCB and its control),
`sHWPBDescDevVAddr`, `scratch_prim_block` (`0x40` bytes in the parameter heap), four list heads
and four list links for partial / complete renders, all 0, and the PID at `+0x40`.

### 4.2 `SGX_CCB_KICK` and the kernel's part [DDK/CAP]

`SGX_DOKICK` (`SGX_CMD_BASE + 3`) carries the kernel CCB command and the sync/status lists.
In both kicks: `sCommand.ui32Data[1]` = the HW render context, all other command words 0
(the kernel fills `ui32ServiceAddress` with the TA handler `0x11d` and the cache control);
`hCCBKernelMemInfo` = the TA client CCB; one destination sync (the colour buffer's), 7 TA and
3 3D status updates; `ui32CCBOffset` = the command's shared block (`+0x58`).

`sgxkick.c:SGXDoKickKM` then writes, inside the client CCB, the shared block
`SGXMKIF_CMDTA_SHARED` (`0x1e0`): the TA/3D TQ sync values and addresses for `hTASyncInfo` /
`h3DSyncInfo`, the source syncs, the TA→3D dependency, copies of the status updates, and
finally `ui32CtrlFlags |= READY` (`0x1`). On the first kick of a scene with destination syncs
it fills the HW destination sync list (`{sAccessDevAddr, count, PVRSRV_DEVICE_SYNC_OBJECT[]}`)
from the kernel sync infos and bumps their write-ops pending. It never touches the rest of the
command. So a kernel that builds the job itself writes the whole `SGXMKIF_CMDTA` and queues a
kernel CCB command `{0x11d, cache control, 0, render context, 0, 0, 0, 0}` **[DDK/infer]**.

### 4.3 Two kicks per frame [CAP]

| | kick 0 | kick 1 |
|---|---|---|
| CMDTA in CCB | `+0x0` | `+0x2c0` |
| `ui32Flags` | `0x71`: first kick, invalidate USE/PDS/data caches | `0x62`: last kick, PDS/data |
| `render_flags` | 0 | `0x400`: render scene |
| VDM stream | `0x0808c000`: clear + triangle | `0x0808c05c`: end of scene |
| `h3DSyncInfo` | none | the pbuffer surface's sync (3D TQ fields filled) |
| TA status [0], [6] | `0x5c`, 1 | `0x70`, 2 |

`glFinish` first flushes the recorded geometry as a TA-only kick, then terminates the scene
with a second, tiny TA kick that asks for the render. Both use the same render details,
RT data and PB.

## 5. Parameter buffer [PSP2/CAP]

`hw_pb_desc` (`0x3c`): flags 0, `ui32NumPages = 0x422`, free list initial head/tail
`0x04220001`, previous `0x04210000`, `evm_page_table_dev_vaddr = 0xc0423000`, current free list
equal to the initial one, thresholds TA `0x432`, ZLS `0x400`, global `0x400`, PDS `0x300`,
`list_pb_block_dev_vaddr` = one `hw_pb_block` {`0x422` pages, head/tail `0x04220001`,
parent = the descriptor}. The command carries its own threshold update block (all 0 here).
`BIFTAReqBase` and `BIF3DReqBase` are both `0xc0000000`, the parameter heap base. The free list
words look like {tail, head} page indices in two 16-bit halves **[infer]**; the EDM initialises
the DPM page table from them (the PB descriptor's page-table-init flag is clear in the
capture, so the EDM or the client did it earlier) **[infer]**.

| `te_mtile_stride` | `0x10` | |

## 8. Render target data [PSP2/CAP]

`hw_rt_data_set` (`0x18` header): pending-count word, complete count, `mtile_width = 8`,
out-of-memory and SPM counters, `num_rt_data = 2`, then two `hw_rt_data` (`0x38`) for
TA/3D overlap. Each has the render context, `num_tile_blocks_per_mt = 1`,
`mt_region_array_size = 0xc0`, the background object (`0xc0464000`, shared), a DPM context
state of its own (`0xd0005000`, `0xd0007000`), shared DPM context control (`0xd0002000`,
`0x40`), OTPM (`0xd0003000`, `0x50`), tail pointers (`0xd0001000`, `0x100`, `tail_size`),
one RT in the array, an RT status word of its own, and `common_status = 0x10`. The
background object holds 1.0 floats and small words: its PDS/ISP layout is open.

## 9. The VDM stream and the programs

### 9.1 VDM control stream [PSP2/CAP]

Every block starts with a type in bits 31:30: link, state, index list, terminate. A state
block is two words: the PDS program address >> 4 in bits 27:0 with a last-task flag (29) and a
complex-geometry flag (28), then, for the plain form, the PDS data size in 16-byte rows
(31:26), SD (25), fence (18), MTE emit (17), USE pipe (15:13), partial (12), partitions
(11:9), secondary (8) and the USE attribute size in 16-byte rows (7:0). An index-list header
holds the primitive type (29:26), presence bits for a third and fourth word (22, 23) and the
index count (21:0); its second word is the index buffer address. Kick 0's stream:

| word | block | decoded |
|---|---|---|
| 0 | state | PDS `0xec011000`, 3 rows of data, MTE emit: copy the clear's MTE state |
| 2 | index list | triangles, 3 indices at `0x080c3000` (16-bit 0, 1, 2): the clear |
| 6 | state, complex, last task | PDS `0xec003040`: the clear's vertex task |
| 8 | state | PDS `0xec011080`: copy the triangle's MTE state |
| 10 | state, secondary | PDS `0xec003120`: secondary (constant) task for the triangle |
| 12 | index list | triangles, 3 indices at `0x080f5000` (0, 1, 2 …): the draw |
| 16 | type 3, complex, last task | PDS `0xec01e000`: the triangle's vertex task; ends kick 0 |

Kick 1's stream (`+0x5c`): a secondary state (PDS `0xec002000`, a no-op USSE task), a
last-task state (PDS `0xec001000`, an MTE state copy of two words), and a plain terminate.
The vertex task of each draw follows its index list as a complex-form state; the complex form
of the second word (here `0x02c00082`, `0x01c00082`) is not decoded yet **[CAP/infer]**.

### 9.2 Vertex side [CAP/RE]

PDS programs are a data segment of 4-dword rows (`ds0[2r]`, `ds0[2r+1]`, `ds1[2r]`,
`ds1[2r+1]`) followed by code (spec §13.8). A USSE code-address word holds a
`EUR_CR_USE_CODE_BASE` index in bits 3:0 and an instruction index from that base above it;
srvinit programs bases 0–9 for pixel code (`0xf4000000` + n × `0x80000`), 10–13 for vertex code
(`0xfc000000` …) and 15 for the EDM **[CAP]**. The clear's words use base 10 (`0x0001010a` →
`0xfc008080`).

- **MTE state copy** (PDS `0xec011000`, `0xec011080`): `doutd` DMAs a state block from the
  PDS vertex heap (`0xec003000` / `0xec003080`; control words `0x02c0000b` / `0x02000018`, whose
  low bits look like a dword count **[infer]**) and `doutu` starts a USSE task
  (`0xfc008700`, `0xfc008a00`) that loads the block and writes it out (`mov.repeat12` /
  `repeat16` + `repeat2` to `o`, then `emitvcbst` and `emitmtest`).
- **Clear vertex task** (PDS `0xec003040`): DMA from `0x08091000` (the clear's three vertices,
  `{x, y, z = 1.0, colour 0xff0000ff}` in screen pixels: (0, 0), (128, 0), (0, 128), a triangle
  covering the 64×64 target) and USSE `0xfc008080`: copy x, y, z, set w = 1.0 from a
  constant, unpack the four colour bytes to floats, `emitvcbvtx`, `emitmtevtx`.
- **Triangle vertex task** (PDS `0xec01e000`): DMA from `0x08091030` (our three vertices,
  `{±0.5, -0.5 / 0.5, 0, 1}`) and USSE `0xfc008d80`: two phases, `ldad.fetch4` the position,
  copy it to `o0..o3`, `emitvcbvtx`, `emitmtevtx` — the compiled `gl_Position = pos`.
- **Secondary task** (PDS `0xec003120`): DMA a block from `0xec0030e0` (control
  `0x02400009`; it holds the floats `2/255`, `1/255`, `1/32767`, `1/65535`, unpacking scales
  **[infer]**) and a one-instruction USSE no-op (`phas.end`).

### 9.3 Pixel side [CAP/RE/infer]

The MTE state blocks reference pixel PDS programs with words holding the data size in 16-byte
rows (31:26) and the program offset from `PDS_EXEC_BASE` (`0xe4000000`) >> 4 in the low bits
**[infer]**: three references decode to programs whose data size matches exactly. In each
state block, word 3 is the secondary program and word 5 the primary one.

- **Clear**: secondary `0x04001800` → `0xe4018000` (USSE `phas.end`, nothing to do); primary
  `0x08000412` → `0xe4004120`: `doutu` USSE `0xf4038170` (`mov.end o0, pa0`) and `douti`
  (iterate the vertex colour into `pa0`). The background object words use the same
  `0x04001800`.
- **Triangle**: secondary `0x0800041a` → `0xe40041a0`: `doutd` the four f16 colour components
  `{1.0, 0.5, 0.25, 1.0}` (at `0xe4004184`) into attribute registers and run USSE `0xf4038300`,
  which packs them to 8-bit (`pcku8f16`) into `pa9`; primary `0x04001802` → `0xe4018020`:
  USSE `0xf4038380`, `mov.end o0, sa9` — the compiled `gl_FragColor = vec4(1, .5, .25, 1)`.

Other state words (`0x0000d4c3`/`0x0000df43`, `0x01d00200`, `0x000000f0`/`0x000010f0`,
`0x00030001`/`0x160f0001`, the viewport scale/offset `32.0, 32.0, 32.0, 32.0, 0.5, 0.5`, …) are
the MTE/ISP/TSP state; not decoded yet.

### 9.4 End of render [CAP/RE]

`EDMPixelPDSExec = 0xe4004000` with `Data = 5` (rows of four dwords: 20 data dwords) and
`Info = 1`. The program tests the event bits in `ir1` against masks in its data and starts
one of three USSE tasks:

- `0xf4035000` (address word `0x0106a000`): **end of tile**. It loads `r0 = 0`,
  `r1 = 0x003f003f` (63, 63), `r2 = 0x001f8000`, `r3 = 0x08087000` — the colour buffer — and
  emits them to the pixel back end with `emitpix1` / `emitpix2.end`. These are the PBE state
  words for a 64×64 RGB565 target; their bitfields are open.
- `0xf4038200`: `ptoff.end`, and `0xf4038280`: `emitpix2.end` with zeros (other events,
  **[infer]** end of render and flush).

## 10. Completion [DDK/CAP/infer]

Each kick carries 7 TA and 3 3D status updates (`{address, value}`, copied into the shared
block). The TA ones are the client's circular-buffer read offsets and a kick counter
(e.g. `*0xe0019000 = 0x5c` then `0x70`, `*0xe0017000 = 1` then 2); the 3D ones are the
fragment buffers' offsets and a render counter. The EDM writes them when the TA (resp. the
render) is done; the client waits on them before reusing buffer space and on the colour
buffer's sync (write-ops complete) for `glFinish`. With the shim writing them at the kick, the
client never waits.

## 11. Open questions (steps 3 and 4)

1. ~~**Complex-form state**~~ — resolved in "State words (differential captures)" (S.1):
   there is no complex-form state block; the two words after each index list are its vertex
   task, and the "type-3 block" is the triangle's vertex task, not a terminate.
2. **MTE / ISP state words** — mostly resolved (S.2–S.5): presence word, the three ISP
   words, pixel PDS pointers (the §9.3 inference holds), region clip, viewport, culling.
   Still open: the output-select and coordinate words, the rest of the MTE control word,
   ISP word 1 bit 12, the high bits of the pixel PDS size word, two-sided stencil (presence
   bits 3–5), the pass type of the scissor mask draws.
3. ~~**PBE words**~~ — resolved (S.7), as in the transfer queue: rectangle, `COUNT`, stride
   in pixel pairs, address; sideband pack mode 3 for RGB565, 0 for ARGB8888, dither bit 10.
4. **Background object** — layout resolved (S.8): the transfer queue's with one TSP layer, a
   full-surface rectangle whose primary program reloads the colour buffer through the
   texture unit. The EDM writes its dwords 0–2 from the special object words at each render
   (§12.3). Open: when the EDM enables it (`ISPBgObj` bit 8), and the texture words.
5. **3D register bitfields** — `TEScreen`, `MTEScreen`, `TEPSG` bit 25 and the ZLS updates
   are pinned (S.6); no other TA or 3D register moved in 66 variations, so `TEAA`,
   `MTECtrl`, `ISPIPFMisc`, `TSPConfig`, `PixelBE`, … need the EDM's register writes (spec
   §13.6) or other variations (multisampling, depth formats, textures).
6. **PB initialisation** (resolved in §12.4). The client builds the page table; the EDM
   can build it from the PB blocks (flag bit 0) and loads the free list and thresholds into
   the DPM. The threshold semantics beyond out-of-memory handling remain open.
7. **The EDM's TA and 3D paths** (resolved in §12.1–§12.3): every field offset the EDM
   uses matches the layouts above.
8. ~~**Minimal job for step 4**~~ — done (§14): one RT data, constant colour in the primary
   pixel program, our own programs, a kernel-built `SGXMKIF_CMDTA`, one TA kick that also
   ends the scene. §12.6 was sufficient as written.

## 12. Microkernel TA/3D handling

How the EDM runs the TA kick and the 3D render, traced in the ukernel (`edm.ta`, kick
address `0x11d`) as `design/sgx545_transfer.md` §3 traced the transfer queue: usse-dis
listing, register names from `tools/usse-dis/regtouch.py`, structure names from the
`kick3d.py` layouts, and `harness/ukernel-extract/edmtrace.py`, which follows command fields
into register writes (`edmtrace.py uk.txt 8e9 acd --seed r0=SGXMKIF_HWRENDERCONTEXT --seed
r1=SGXMKIF_CMDTA --seed r14=hw_rt_data` lists the whole TA kick). The routines are
named in `sgx545_labels.r2`.

Conventions for this section:

- Addresses are **instruction indices** from the EDM code base (byte offset = index × 8), the
  form the branch targets and kick addresses use. `insn 0x8e9` is `edm.ta.kick`.
- `CMDTA dwN`, `rd dwN`, `rtdata dwN`, `ctx dwN`, `pb dwN` are dword offsets into
  `SGXMKIF_CMDTA`, `hw_render_details`, `hw_rt_data`, `SGXMKIF_HWRENDERCONTEXT`
  and `hw_pb_desc` (§4–§8 layouts; every offset the EDM uses lands on a named field,
  which confirms the [PSP2] layouts for this ukernel **[RE]**).
- `TA3DCtl[k]` is dword *k* of the TA/3D control block in memory (`[sa0,+#k]`); `saN` is the
  secondary-attribute register, a separate copy that PDS #11 loads at boot (spec §13.9).
- Flag bits are written in plain words with their value, as in `kick3d.FLAGS`.

### 12.1 Events and deferred work [RE]

Every event runs PDS #13 (spec §13.8), which passes two input words to the EDM task: `pa0`
and `pa1`. **`pa1` is not `EVENT_STATUS`**: it has its own, compact bit layout. Pairing each
`pa1` test with the `EVENT_HOST_CLEAR` value its handler acknowledges gives:

| `pa1` bit | event (`EVENT_STATUS` bit acknowledged) | handled at |
|---|---|---|
| 4 (`0x10`) | `PIXELBE_END_RENDER` (`0x40000`): the render finished | insn `0xe21`, `0xebb` |
| 7 (`0x80`) | `BREAKPOINT` (`0x8000`): ISP visibility-test breakpoint | `0xe5a`, `0xecd` |
| 8 (`0x100`) | host kick (`EVENT_KICK`) | `0x98` (`edm.ccb.fetch`) |
| 9 (`0x200`) | `TA_FINISHED` (`0x2000`) | `0x6f`, `0x5e9` |
| 10 (`0x400`) | `TA_TERMINATE` (`0x1000`): TA stopped after an out-of-memory | `0xadd`, `0xafb` |
| 20, 21 | `DPM_OUT_OF_MEMORY_GBL` / `_MT` (`0x6`) | `0xad1`, `0xaf0` |
| 22 (`0x400000`) | `DPM_3D_MEM_FREE` (`0x1`): the 3D deallocation finished | `0xe1a`, `0xe89` |

So the `EVENT_STATUS` names that spec §13.8 attaches to the `pa1` bits of the fast paths
(`DPM_INITEND`, `DPM_STATE_STORE`, ...) are those of the same bit positions in
`EVENT_STATUS`, not the events; transfer §3.1 step 7 had already found bit 4 to be
end-of-render. The request bits of `edm.request` (`TA3DCtl[31]`) that matter here:

| request | posted by | PDS #14 task → routine |
|---|---|---|
| `0x1` | `pa1` bit 22 | `dpm_store` → `edm.3d.mem_free` |
| `0x2` | `pa1` bit 4 | `dpm_store` → `edm.3d.end_render` |
| `0x8` | `pa1` bit 7 | `dpm_store` → `edm.isp.vistest` |
| `0x10`, `0x20` | `pa1` bits 20, 21 | `csw_flush` → `edm.ta.oom` (`0xb50`) |
| `0x40` | `pa1` bit 10; the partial-render paths | `csw_flush` → `edm.ta.terminated` (`0xc23`) |
| `0x80` | `pa1` bit 9 | `dpm_clear` → `edm.ta.finished` (`0x606`) |
| `0x20000` | `edm.post_ta` (`0x1592`): TA queue not empty | `dpm_clear` → `edm.ta.pick` (`0x6f5`) |
| `0x40000` | `edm.post_3d` (`0x159e`): 3D or transfer queue | `dpm_store` → `edm.3d.schedule` |
| `0x80000` | `edm.3d.complete` after a partial render | `csw_flush` → `edm.spm.resume` (`0xdbf`) |

This answers spec §13.11's question about the directly posted bits `0x20000`, `0x40000` and
`0x80000`. Every handler ends the task (`edm.task.end`, `0x1974`); work continues through the
next event or request, never by waiting inside a task, except for the short register polls
listed below.

The EDM keeps one TA and one 3D job in flight. Its state words: `sa8` (TA side: bit 0 TA
running, bit 11 out-of-memory pending, bits 5, 9, 10, 18, 22 partial-render states) and `sa9`
(3D side: bit 0 3D running, bit 1 partial render, bit 2 transfer, bit 4 render in flight,
bit 5 deallocation pending, bit 6 out-of-memory waiting for the 3D). The queues are lists of
contexts: transfer `sa13`/`sa14`, TA `sa15`/`sa16`, 3D `sa17`/`sa18` (head/tail, priority 0).

### 12.2 The TA path

**Kernel CCB handler (`edm.ta`, insn `0x11d`–`0x139`) [RE].** `r7` = `ui32Data[1]` = the HW
render context. It increments `ctx.ta_count` (dw5). If the count was already non-zero, or
`ctx.hw_partial_renders_head` (dw8) is set, the context is already queued; otherwise it is
appended to the TA queue (`sa15`/`sa16`, linked through `ctx.prev_partial_dev_addr` /
`next_partial_dev_addr`, dw12/13). Then the scheduler (`0x161`) posts `0x20000`. **The handler
reads nothing else**: one kernel CCB command stands for one `SGXMKIF_CMDTA` waiting in the
context's TA client CCB, and the host never passes the command's address.

**Pick (`edm.ta.pick`, `0x6f5`–`0x7b0`) [RE].** Nothing happens while a cleanup is pending
(`sa10 & 3`) or `sa8` bit 2 or 18 is set. For each context in the TA queue:

1. skip it if `ctx.ta_count` is 0 or `ctx.common.ui32Flags & 0x10` (suspend);
2. the command is at `ctx.ta_ccb_base_dev_addr + CCBCtl[1]`, i.e. `ta_ccb_ctl_dev_addr` points at
   `{write offset, read offset}` and the read offset is in bytes, as for the transfer CCB;
3. it must have `shared_state.ui32CtrlFlags & 1` (`READY`, which `SGXDoKickKM` sets last);
4. the TA TQ sync (CMDTA dw25–28) must be complete (`*WComp == WPend` and `*RComp == RPend`),
   unless its address is 0;
5. with TA flag `0x400` (dependent TA), `*sTA3DDependency.WComp == WPend` (dw68/69);
6. a first kick or resume (flags `0x5`) needs `rtdata.common_status & 0x10`: the RT data
   is free, no render on it is outstanding (`rtdata` = CMDTA dw17);
7. the first destination sync object (CMDTA dw15, if not 0) and every source sync
   (dw33/34…) must be complete, the same test as 4;
8. with TA flag `0x2000` (PB threshold update) the thresholds of CMDTA dw10–13 are copied into
   the PB descriptor (dw10–13) and `pb.pb_flags |= 2`, but only while the 3D is idle;
9. it kicks only if no TA is running (`sa8` bit 0). An aborted RT data (`CommonStatus & 0x40`)
   or render flag `0x2` (abort) takes `edm.ta.abort` (`0x80c`) instead: the command completes
   (TATQ read-op, TA status words, `SW_EVENT`) without running.

**Kick (`edm.ta.kick`, `0x8e9`–`0xacd`) [RE], in order:**

1. `TA3DCtl[27]` = ctx, `[24]` = cmd, `[26]` = render details (CMDTA dw14), `[50]` =
   `ctx.ui32PID`; `rtdata.hw_render_details_dev_addr` (rtdata dw1) = render details. The client
   does not need to fill that RT data field.
2. If the previous TA used another RT data (`TA3DCtl[25]`), its DPM context is stored
   (`dpm.ctx_store`) through its own address space and its DPM slot freed (`0x8f8`–`0x918`).
3. **First kick** (flag `0x1`): pulse `SOFT_RESET` = `TA_RESET` (4), then 0 (`0x91d`).
4. **Parameter buffer** (`0x91f`–`0x959`), §12.4: unless the context's PB
   (`ctx.sHWPBDescDevVAddr`, dw6) is already the one loaded in the TA (`TA3DCtl[46]`), store
   the old one's free list and load the new one (`pb.ta_store`, `pb.init_page_table`,
   `pb.ta_load`, with the EDM's memory accesses switched to the context's address space by
   `bif.edm_index`); if it is already loaded, apply a pending threshold update
   (`pb.ta_thresholds`).
5. **TA registers** (`0x95a`–`0x985`): CMDTA dw142–169 (`ta_regs`) are written in structure
   order, one fixed `str` each, no table:

   | CMDTA field | register | CMDTA field | register |
   |---|---|---|---|
   | `teaa` | `TE_AA` | `usest_range` | `USE_ST_RANGE` |
   | `te_mtile_1` / `2` | `TE_MTILE1` / `2` | `bif_ta_req_base` | `BIF_TA_REQ_BASE` |
   | `te_screen` | `TE_SCREEN` | `gsg_stride` / `Base` / `Wrap` | `GSG` / `_BASE` / `_WRAP` |
   | `te_mtile_stride` | `TE_MTILE` | `gsg_state_store` | `GSG_STORE` |
   | `te_psg` | `te_psg` | `ui32MTE1stPhaseCompGeom*` | `MTE_1ST_PHASE_COMPLEX_*` |
   | `vdm_ctrl_stream_base` | `VDM_CTRL_STREAM_BASE` | `vtx_buf_write_pointer_pds_prog` | (1) |
   | `mte_ctrl` | `MTE_CTRL` | `sc_word_copy_program` | `VDM_SCWORDCP_PDSPROG` |
   | `te_psg_rgn_base` | `TE_PSGREGION_BASE` | `itp_program` | `VDM_ITP_PDSPROG` |
   | `te_tpc_base` | `TE_TPC_BASE` | `tart_max` | `DPM_TA_RENDER_TARGET_MAX` |
   | `mtew_compare` / `WClamp` | `MTE_WCOMPARE` / `_WCLAMP` | `te_tpc` | `TE_TPC` |
   | `mte_screen` | `MTE_SCREEN` | `mtems_ctrl` | `MTE_MULTISAMPLECTL` |
   | `useld_redirect` | `USE_LD_REDIRECT` | | |

   (1) `VDM_VTXBUF_WRPTR_PDSPROG`.

6. `DMS_CTRL` bits 31:27 = `num_vertex_partitions` (CMDTA dw5, pre-shifted: `0x50000000`
   is 10) (`0x986`).
7. `bif.map_context(ctx, TA)`: find or assign a BIF directory list for `ctx.sPDDevPAddr` and
   set `BIF_BANK0.INDEX_TA`; with `NEWCONTEXT` (flag `0x1`) it clears the flag and invalidates
   the caches (transfer §3.1 step 6 describes the same routine for the 3D index).
8. Cache invalidations by TA flag: `0x40` data (`CACHE_CTRL` bit 28, wait
   `MADD_CACHE_INVALCOMPLETE`), `0x20` PDS (`PDS_INV0`, `PDS_INV_CSC`, wait
   `PDS_CACHE_STATUS & 0x27`), `0x10` USE (`USE_CACHE`).
9. **DPM context slot** (`0x9b7`–`0x9f6`): the DPM holds two contexts; `TA3DCtl[20]`/`[21]`
   record which RT data owns each. The TA takes the slot that already holds its RT data, else
   a free one, else the one the 3D is not using (`DPM_STATE_CONTEXT_ID` bit 1 is the 3D's
   slot, bit 2 the TA's, bit 0 the one DPM tasks address); an evicted RT data is stored first.
   `TA3DCtl[25]` = RT data.
10. **First kick or resume after free** (flags `0x9`, `0xa0e`–`0xa60`):
    `DPM_STATE_TABLE_CONTEXT0/1_BASE` = `rtdata.context_state_dev_addr` (dw5),
    `DPM_CONTROL_TABLE_BASE` = `rtdata.context_control_dev_addr` (dw6); then for each of the
    `rtdata.num_rts_in_array` render targets `DPM_TASK_STATE` = `DPM_TASK_CONTROL` =
    `(rt << 3) | 2` (clear), waiting for `DPM_STATE_CLEAR | DPM_CONTROL_CLEAR`; then
    `MTE_OTPM_CSM_BASE` = `rtdata.context_otpm_dev_addr` (dw7), `MTE_OTPM_OP` = 9, waiting for
    `OTPM_INV` and `EVENT_STATUS2.OTPM_MEM_CLEARED`. The DPM task codes are 1 store, 2 clear,
    4 load (`dpm.state_*`, `0x1741`–`0x1755`). Otherwise, if the slot did not hold this RT
    data, `dpm.ctx_load` restores its state, control and OTPM.
11. `TE_STATE` = `rd.te_state` (rd dw73); `te_psg |= 0x01000000`, and `|= 0x200000` if
    `rtdata.common_status` bit 8 is set (`0xa61`–`0xa6e`).
12. First kick or resume (flags `0x5`): `CommonStatus &= ~0xff0` and the
    `num_rts_in_array` RT status words (`rtdata.rt_status_dev_addr`) are zeroed.
13. `sa8 |= 1` (TA running); the context moves to the head of the TA queue.
14. `edm.ta.cmd_to_rd` (`0x7b1`): copies into the render details `render_flags`, the
    TA→3D dependency (with render flag `0x200`), `ui32FrameNum` (also `TA3DCtl[41]`), the 3D
    TQ sync (CMDTA dw29–32 → rd dw57–60), `hw_dst_sync_list_dev_addr`, the source syncs,
    `vis_test_results_dev_addr`, the Z/S strides, `spec_object[0..2]` and the 3D status
    updates. The `num_3d_regs` pairs of `reg_updates_3d` (dw170…) are **memory** writes,
    `*address = value`, not register writes: a way to patch the render details per kick.
15. HWPerf `TA_START` (type 3, with the DPM page count); with TA flag `0x1000`,
    `HostCtl[16]` = 500. Then **`VDM_START` = 1** (`0xacc`).

**TA finished (`edm.ta.finished`, `0x606`–`0x6f4`) [RE].** `pa1` bit 9 → request `0x80` →
`EVENT_HOST_CLEAR = TA_FINISHED`. Unless a partial render is pending (`sa8` bits 9/10, which
post `0x40` instead), at `0x643`:

1. `sa8 &= ~0x79d` (TA idle); `shared_state.ui32CtrlFlags &= ~READY`;
2. `*sTATQSyncReadOpsCompleteDevVAddr = ui32TATQSyncReadOpsPendingVal + 1` (dw27/28, if set);
3. `pb.alloc_pages` (pb dw5) = `DPM_PAGE_STATUS` bits 31:16, the pages in use;
4. the `ui32NumTAStatusVals` pairs of `sCtlTAStatusInfo`: `*sStatusDevAddr = ui32StatusValue`;
5. **`EVENT_STATUS = SW_EVENT`** (`0x4000`): the host interrupt;
6. last kick (flag `0x2`): `CommonStatus |= 0x20` (scene closed); unless render flag `0x8`
   (no dealloc), `TA3DCtl[25]` = 0 and `TE_TPCCONTROL` = `0x40000000`, waiting for
   `TPC_FLUSH` (the tail pointer cache is flushed to memory);
7. first kick or resume: the render details are appended to the context's pending-render list
   (`ctx.hw_partial_renders_head/Tail`, dw8/9, linked through rd dw74/75);
8. not the last kick (or no dealloc): `rd.te_state` = `TE_STATE`, so the next kick of the
   scene resumes the tiling engine; not the last kick: the RT data set's dword 1
   (`complete_count`) is incremented, and that is all;
9. last kick: render flag `0x1` (no render) frees the scene's memory (`dpm.free_scene`,
   `0x187c`: `DPM_FREE_CONTEXT`, `TE_TPCCONTROL` = `0x80000000`, wait `DPM_TA_MEM_FREE |
   TPC_CLEAR`); then **`edm.3d.queue_render(ctx, rd)`** (`0x1942`) moves the render details to
   the context's ready list (`hw_complete_renders_head/Tail`, dw10/11) and, if that list was
   empty, appends the context to the 3D queue (`sa17`/`sa18`, linked through dw14/15);
10. `edm.post_3d`; `edm.ta.ccb_advance` (`0x7fc`): `CCBCtl[1] = (CCBCtl[1] + cmd.ui32Size) &
    0xffff` (a 64 KiB TA CCB) and `ctx.ta_count--`; the context leaves the TA queue and is
    re-appended if it has more kicks or pending renders; `edm.post_ta`.

**Out of memory and partial renders [RE, summary].** `pa1` bits 20/21 →
`edm.ta.oom` (`0xb50`): `sa8 |= 0x800`, `rt_data_set.ui32NumOutOfMemSignals` (dword 3) and
`CommonStatus |= 0x80`. If a render can free memory soon (the 3D runs, or the context has a
ready render) it waits for it (`sa9 |= 0x40`). Otherwise it first grows the TA's share of the
global list (`DPM_TA_GLOBAL_LIST`, `DPM_ZLS_PAGE_THRESHOLD`, with `dpm.ta_alloc_pause`/
`_resume`) and retries with `DPM_OUTOFMEM` = 1; when that is exhausted it aborts the current
macrotile (`MTE_OTPM_OP` = 1, `DPM_ABORT_STATUS_MTILE` saved in `TA3DCtl[39]`/`[40]`,
`DPM_OUTOFMEM` = 4, `DMS_CTRL |= 1`). The TA then stops (`pa1` bit 10) and
`edm.ta.terminated` (`0xc23`) starts a **partial render** of what was tiled so far, through
the RT data's ZLS external-Z region headers (`ISP2_ZLS_EXTZ_RGN_BASE`, HWPerf type 8, `sa9 |=
0x33`, `ISP_START_RENDER` at `0xdb3`). Its completion posts `0x80000`; `edm.spm.resume`
(`0xdbf`) clears the DPM control state (`DPM_TASK_CONTROL` = 2, bracketed by
`DPM_LSS_PARTIAL_CONTEXT`), sets bit 1 of the macrotile's RT status word (depth stored, so the
final render loads it **[infer]**) and restarts the TA with `DPM_OUTOFMEM` = 1. The
thresholds of the PB descriptor are the only host input; a minimal job
avoids all of this by giving the scene enough pages.

### 12.3 The 3D path

**Scheduling [RE].** There is **no 3D command**: the render is queued by the EDM itself when
the last TA kick of a scene finishes (step 9 above). `edm.post_3d` posts `0x40000`; PDS #14
runs `edm.work.dpm_store`, whose `0x40000` branch calls `edm.3d.schedule` (`0x1035`). That
bails out on a pending cleanup or `sa9 & 0xa`, kicks nothing while a render runs, tries the
transfer queue (`edm.transfer.pick`) first and then `edm.3d.pick` (`0x105d`), which walks the
3D queue: for a non-suspended context it takes the first render details of the ready list
(`ctx` dw10) and checks, for the RT index `rd.next_rt_idx` (dw66): the destination sync
object of that index (`rd.hw_dst_sync_list_dev_addr` + 8 + 16 × index: `*WComp == WPend`,
`*RComp == RPend`), the 3D TQ sync (rd dw57–60) and the source syncs (rd dw90…). With the RT
data aborted or render flags `0x3` (no render / abort) it completes the render details
without rendering (`0x10d7`).

**Kick (`edm.3d.kick`, `0x112b`–`0x12db`) [RE], in order:**

1. `TA3DCtl[51]` = PID, `[30]` = RT index, `[29]` = render details, `[42]` = frame number,
   `sa7` = ctx, `sa6` = priority.
2. DPM slot for the RT data (`DPM_STATE_CONTEXT_ID` bit 1); if another RT data held it, it is
   stored, and this one is loaded with `dpm.ctx_load` through the 3D's address space
   (`BIF_BANK_SET` bit 9). When the TA just finished on the same RT data it is still
   resident and only `bif.map_context(ctx, 3D)` runs.
3. 3D parameter buffer (`0x118d`–`0x11ad`): unless `TA3DCtl[47]` is already the context's PB,
   store the old one and `pb.3d_load` the new one (§12.4).
4. `DPM_3D_DEALLOCATE` = 3 and `sa9 |= 0x30` (free the scene's pages during the render),
   or 0 and `sa9 |= 0x10` with render flag `0x8` (no dealloc, the scene continues).
5. `ISP_VISTEST_CTRL` = `0xff`, `ISP_RENDBOX1` = `ISP_RENDBOX2` = `ISP_RENDER` = 0.
6. **The 52 dwords of `rd.regs_3d` are written in structure order** (`0x11bf`–`0x1211`):
   `BIF_3D_REQ_BASE`, `BIF_ZLS_REQ_BASE`, `PIXELBE`, `ISP_IPFMISC`, `3D_AA_MODE`,
   `ISP_DBIAS0..2`, `ISP_RGN_BASE`, `DOUBLE_PIXEL_PARTITIONS`, `ISP2_ZLS_EXTZ_RGN_BASE`,
   `isp_zls_ctl`, `ISP_ZLOAD_BASE`, `ISP_ZSTORE_BASE`, `ISP_STENCIL_LOAD_BASE`,
   `ISP_STENCIL_STORE_BASE`, `ISP_BGOBJDEPTH`, `ISP_BGOBJ`, `ISP_BGOBJTAG`,
   `ISP_MULTISAMPLECTL2`, `ISP_MULTISAMPLECTL`, `ISP_TAGCTRL`, `TSP_CONFIG`,
   **`EVENT_PIXEL_PDS_EXEC` / `_DATA` / `_INFO`** (from `ui32EDMPixelPDS*`), `ISP_FPUCTRL`, the
   USE filter registers, `TPU_YUV*`, `TPU_LUMA0..2` and `ISP_DEPTHSORT`. They are copied
   verbatim, so the EDM gives no bitfield information about them. Unlike the transfer
   (transfer §3.3), **`PDS_EXEC_BASE` is not written**: the pixel programs are relative to the
   value the last transfer (or the init script) left.
7. `DPM_3D_RENDER_TARGET_INDEX` = RT index; for index > 0, `ISP_RGN_BASE += index ×
   rtdata.rgn_stride` and the Z/S load/store bases `+= index × rd.ui32Z/SBufferStride`.
8. If `rd.pix_event_update_dev_addr` is set, the two dwords at `hw_pix_event_update_list_dev_addr +
   8 × index` are written there (through the 3D's address space): per-RT patching of the
   end-of-tile program's PBE words.
9. Render flag `0x10` (Z-only): `isp_zls_ctl |= 1`. `DMS_CTRL` bits 26:22 =
   `rd.num_pixel_partitions`; `DPM_PARTIAL_RENDER` = 0.
10. Invalidate the data cache (`CACHE_CTRL` bit 28 and its event), `TSP_PARAMETER_CACHE`,
    `USE_CACHE` (once per task) and the PDS caches (`PDS_INV1`, `PDS_INV_CSC`, wait
    `PDS_CACHE_STATUS & 0x4b`).
11. Depth/stencil load and store bits of `isp_zls_ctl` are adjusted from render flags `0x80`
    (depth buffer) / `0x100` (stencil buffer) and the RT status word's bit 1 (contents stored
    by an earlier partial render). With both flags clear and `isp_zls_ctl` = 0 nothing is
    loaded or stored.
12. **Background object**: through the 3D's address space, dwords 0–2 of
    `rtdata.bg_obj_base_dev_addr` = `rd.spec_object[0]`, `[1]` and the word at
    `rd.hw_bg_obj_prim_pds_update_list_dev_addr + 4 × index` (`0x128d`–`0x1296`). In the capture the
    first three dwords of the background object are 0 at the kick and the update list holds
    `0x0c00040e` = `spec_object[2]` **[CAP]**: the client leaves them for the EDM.
13. `TA3DCtl[28]` = RT data, `sa9 |= 1` (3D running), the context moves to the head of the 3D
    queue, HWPerf `3D_START` (type 4), **`ISP_START_RENDER` = 1** (`0x12da`).

**Completion [RE].** `pa1` bit 4 (`PIXELBE_END_RENDER`) → `edm.3d.end_render` (`0xebb`):
transfers go to their own completion (`sa9` bit 2); for a render it waits for a clock-gating
idle bit, clears `sa9` bit 4 and, if the deallocation is still running (`sa9` bit 5), waits
for `pa1` bit 22 (`DPM_3D_MEM_FREE`, `edm.3d.mem_free`). When both have arrived,
`edm.3d.complete` (`0xfd1`) clears `sa9` and, for a full render:

1. render flag `0x20` (get visibility results): accumulate the visibility counters
   (`edm.isp.vistest`);
2. `edm.3d.syncs_done` (`0xf45`): `*WComp = WPend + 1` of the RT index's destination sync
   object; if `num_rts` > index + 1, `next_rt_idx` = index + 1 and the same render details
   stay queued for the next render target; otherwise `next_rt_idx` = 0 and, with render flag
   `0x200`, the TA→3D dependency's `*WComp = WPend + 1`; the 3D TQ sync's `*RComp = RPend +
   1`; every source sync's `*RComp = RPend + 1`; **the `ui32Num3DStatusVals` pairs of
   `sCtl3DStatusInfo`: `*sStatusDevAddr = ui32StatusValue`**; RT status word `|= 1`;
3. `edm.3d.scene_done` (`0xf9d`, last RT only): `rtdata.common_status` = (old `& ~0x60`)
   `| 0x10` (free again) `| (render flags >> 14) << 12`; with render flag `0x400` (render
   scene) the RT data set's dword 1 is incremented; `rtdata.hw_render_details_dev_addr` = 0; unless
   render flags `0xc` (mid-scene / no dealloc), `*rd.sAccessDevAddr = 0` and the RT data
   leaves its DPM slot (`TA3DCtl[20]`/`[21]`); with a destination sync list,
   `*list.sAccessDevAddr = 0`; **`EVENT_STATUS = SW_EVENT`** (also after each earlier RT of a
   multi-RT render);
4. the render details leave the ready list, the context leaves the 3D queue (re-appended if
   more renders are ready), and the TA and 3D schedulers run again.

A partial render instead posts `0x80000` (§12.2). The HWPerf types seen: 2 transfer, 3 TA,
4 render, 8 partial render, with bit 28 set for the end record.

**The two kicks of the capture [CAP/RE].** Kick 0 (flags first kick + invalidations, render
flags 0, the clear and the triangle) runs the TA; at its end the EDM saves `TE_STATE` into the
render details and does nothing else. Kick 1 (flags last kick + invalidations, render flags
`0x400`, a VDM stream of two state blocks and a terminate, `te_psg` bit 22 set) resumes the
TA on the same RT data and DPM context; its `TA_FINISHED` queues the render. **The render is
triggered by TA flag `0x2` (last kick), not by render flag `0x400`**, which the EDM only uses
for the completion count. One kick with flags first + last and the whole stream (draws, then
the terminate, with `TEPSG` bit 22) takes the same paths: TA reset and DPM clear, tiling, then
the render at `TA_FINISHED` **[RE/infer]**.

### 12.4 Parameter buffer and DPM: host and EDM duties

**What the EDM does [RE]:**

- **Load into the TA** (`pb.ta_load`, `0x16a2`): `TA3DCtl[46]` = descriptor;
  `DPM_TA_ALLOC_PAGE_TABLE_BASE` = `evm_page_table_dev_vaddr & ~0xf`; `DPM_TA_ALLOC_FREE_LIST` =
  `free_list_ht`; `DPM_TA_ALLOC` = `free_list_prev`;
  `DPM_START_OF_CONTEXT_PAGES_ALLOCATED` = `local_pages | global_pages << 16`;
  `DPM_TA_PAGE_THRESHOLD`, `DPM_ZLS_PAGE_THRESHOLD`, `DPM_PDS_PAGE_THRESHOLD` = the TA, ZLS and
  PDS thresholds; `DPM_TA_GLOBAL_LIST` = `(global_threshold & 0xffff) | 0x10000`;
  `DPM_CONTEXT_PB_BASE` = which of the TA, 3D and third PB slots (`TA3DCtl[46..48]`) share a
  descriptor; then `DPM_TASK_TA_FREE` = 1, waiting for `EVENT_STATUS2.DPM_TA_FREE_LOAD`.
- **Load into the 3D** (`pb.3d_load`, `0x16e9`): the same into `DPM_3D_PAGE_TABLE_BASE`,
  `DPM_3D_FREE_LIST`, `DPM_3D`, `DPM_START_OF_3D_CONTEXT_PAGES_ALLOCATED`, then
  `DPM_TASK_3D_FREE`. `TA3DCtl[47]` = descriptor.
- **Store** (`pb.ta_store` `0x168d`, `pb.3d_store` `0x16d4`): the free-list status registers
  back into `free_list_ht`, `free_list_prev` (status 2 `<< 16`), `local_pages`,
  `global_pages`. When the TA and 3D share one descriptor the other side's state is stored
  first, with that pipe paused (`edm.pipe.pause`/`resume`, `0x15bc`/`0x15ad`), so the free list
  stays consistent. At each TA end `alloc_pages` = pages in use.
- **Thresholds** (`pb.ta_thresholds`, `0x1665`): with `pb_flags` bit 1 the thresholds are
  reloaded and bits 0–1 cleared.
- **Page table** (`pb.init_page_table`, `0x170d`): with `pb_flags` bit 0 the EDM resets
  `free_list_ht`/`Prev` from the initial values, zeroes the page counts and links the page
  table from the PB block list (`ui32PageCount`, the head in `ui32HeadTail` bits 15:0,
  `next_hw_pb_block_dev_vaddr`), each entry `previous << 16 | next`, `0xffff` at both ends. Its loop
  ORs a bit 18 into the index register whose effect is not pinned **[RE/infer]**, so
  building the table on the host, as the client does, is the safer choice.
- **DPM contexts**: clear on a first kick, store/load when RT data change slots
  (`dpm.ctx_store` / `dpm.ctx_load`: state table, control table, OTPM and tail pointer cache,
  with `TE_TPCCONTROL` flush), free without render (`dpm.free_scene`), deallocate during the
  render (`DPM_3D_DEALLOCATE`), and all out-of-memory handling (§12.2).

**What the host provides [CAP/RE/infer]:**

- The pages, contiguous in the parameter heap, and the **page table**: one 32-bit entry per
  4 KiB page of the heap, indexed by `(address − BIF_TA_REQ_BASE) / 4096`. The captured table
  links pages 1–`0x422` (`0xc0001000` …, exactly the PB allocation): entry *i* =
  `(i − 1) << 16 | (i + 1)`, entry 1 = `0xffff0002`, the last = `0x0421ffff`, the rest 0
  **[CAP]**. The table itself sits in the same heap after the pages.
- The **descriptor**: `ui32NumPages`; `free_list_initial_ht` = `free_list_ht` = tail
  `<< 16 | head` (`0x04220001`); `free_list_initial_prev` = `free_list_prev` = the page
  before the tail `<< 16` (`0x04210000`), the value the EDM writes to `DPM_TA_ALLOC`;
  `evm_page_table_dev_vaddr`; local/global pages and `alloc_pages` 0; the four thresholds
  (captured TA `0x432`, ZLS `0x400`, global `0x400`, PDS `0x300` for `0x422` pages); one PB
  block `{page count, head/tail, parent}`; `pb_flags` 0 if the table is prebuilt.
- `BIF_TA_REQ_BASE` (CMDTA) and `BIF_3D_REQ_BASE` (render details) = the parameter heap base.
- Zeroed TADATA buffers for the RT data: DPM context state (one per RT data), DPM context
  control, OTPM, tail pointers (`tail_size` bytes), region headers, ZLS external-Z region
  headers, and zeroed RT status words. The EDM clears the DPM state and the OTPM itself on a
  first kick, but never zeroes the tail pointers or the region headers except on the abort
  path **[RE]**.

### 12.5 Memory and address spaces [RE/infer]

The EDM reads the render context, the TA CCB and its control, the command, the render
details, the RT data and set, the PB descriptor and block, the sync objects and writes the
status words through **its own** directory list (15). It switches `BIF_BANK0.INDEX_EDM` to the
context's list (`bif.edm_index`) only to build the page table and load the PB (TA list), to
zero the tail pointers on the abort path, and to write the pixel-event update and the
background-object words (3D list). So the KERNEL_DATA objects (render context, render
details, RT data, PB descriptor) must be mapped at the same addresses in the EDM's and the
context's page tables, and the page table and background object must be in the context's.
The DDK achieves this with shared heaps **[DDK]**.

## 13. State words (differential captures)

Method. `tri` takes options that change one piece of GL state at a time
(`harness/ukernel-extract/triopts.h`); `variations3d.txt` lists 66 runs, captured with
`capture3d.sh` (README "Differential captures", manifest in `extracted/gles2_tri/`).
`state3d.py` names every state-carrying word of both kicks under a stable path and
`diff3d.py` compares each run with `base`, hiding words that only point somewhere else in a
moved object. `base2` (a second identical run) extracts to exactly the same words. In this
section **[CAP `x`]** means "the variation `x` (option `x` of `tri`) flips it"; `size=*`,
`depth=*` … stand for the whole family. The field names are ours unless tagged [DDK]. Where
a field boundary was first suggested by the [PSP2] headers (the presence-word order, the
`doutd` word, the vertex-task words), it is listed only with the capture that confirms it.
Decoders and tests: `state3d.py` (`DECODERS`, `decode_*`), `kick3d.decode_vertex_pds`.

### S.1 The VDM stream, corrected

There is no complex-form state block in any capture. The two words that §9.1 read as a
"complex, last task" state after each index list, and the "type 3" block at word 16 of
kick 0, are the **vertex task of the index list**: an index list block is the header, the
index base, the optional third and fourth words (present bits 22 and 23: `0xf0000000` and
`0x003fffff` in every capture), then two vertex-task words **[CAP]**. Kick 0 goes on after
the triangle's vertex task with a no-op secondary state, the end-of-scene state (S.4) and
the real terminate at word 22; kick 1 repeats those five words.

| word | bits | field | evidence |
|---|---|---|---|
| 1 | 31:28 | partition size **[infer]** | 7: screen-space draws; 15: compiled shaders |
| 1 | 27:0 | PDS vertex program address >> 4 | data size below fits every program |
| 2 | 31:24 | output vertex size, 4-dword units | 1 → 2 **[CAP `varying`, `prim=points`]** |
| 2 | 23:22 | 3 in every capture | |
| 2 | 14:7 | USE attribute size, 16-byte rows | 1 → 2 **[CAP `varying`]** |
| 2 | 6:0 | PDS data size, 16-byte rows | 2 → 3 **[CAP `varying`]** (code starts there) |

The vertex PDS program DMAs each attribute of one vertex with `doutd` from the vertex buffer
(base + vertex index × stride, `movsa` adding `ir0 × stride`); the second attribute of
`varying` lands at attribute offset 4 **[CAP]**. The index list header's primitive type
(29:26) is 0 triangles, 1 lines, 2 points, 3 strip, 4 fan, and 21:0 the vertex count
**[CAP `prim=*`]**; the driver turns a line strip into a line list. `prim=two` only changes
the count. Plain state blocks never set the complex bit (28); their second word decodes as
in §9.1.

### S.2 MTE state blocks

A state program `doutd`s a block from the PDS vertex heap into USSE attributes and starts a
USSE task that copies them to the outputs and `emitmtest`s them (§9.2). `doutd`'s second
word is burst size − 1 (3:0), lines − 1 (7:4), the destination attribute offset (19:8) and
stride − 1 (29:22) **[CAP]**: the clear's `0x02c0000b` copies 12 dwords, the triangle's
`0x02000018` 2 × 9 = 18, which are the lengths of the USSE copy loops; a 19-word stencil
block takes two bursts (16 + 3). The end-of-scene program builds its two-word block with
`douta` instead (value, then the attribute offset in 19:8).

The block starts with a **presence word**; every set bit adds its words, in bit order
**[CAP]**: the clear's `0xd4c3` is 12 words, the triangle's `0xdf43` 18, stencil adds bit 2
and one word, a scissor bit 7 and two.

| bit | words | name in `state3d` | content |
|---|---|---|---|
| 0 | 1 | `isp0` | ISP word 0 (S.3) |
| 1 | 1 | `isp1` | ISP word 1: colour mask (S.3) |
| 2 | 1 | `isp2` | ISP word 2: stencil (S.3) **[CAP `stencil=*`]** |
| 6 | 3 | `pds_sec`, `pds_size`, `pds_pri` | pixel programs (S.5) |
| 7 | 2 | `clip0`, `clip1` | region clip (S.4) **[CAP `scissor=*`]** |
| 8 | 6 | `vp0`…`vp5` | viewport (S.4) |
| 9 | 1 | `wrap` | 0 in every capture |
| 10 | 1 | `outsel` | output selects (S.4) |
| 11 | 1 | `wclamp` | `0x3727c5ac` (1e-5) in every capture |
| 12 | 1 | `mtectl` | MTE control: culling (S.4) |
| 13 | 1 | `term` | end of scene (S.4) |
| 14, 15 | 1, 1 | `coordsize`, `coordfmt` | iterated coordinate sets (S.4) |

Bits 3–5 (back-face copies of the ISP words for two-sided stencil **[infer]**) and 16 and up
never appear. Blocks seen: the clear `0xd4c3`; a draw `0xdf43`, `0xdf47` with stencil,
`0xdfc3` with a scissor; the scissor mask draws `0xd485`; the end of scene `0x2000`.

### S.3 ISP words: depth, stencil, colour mask, blending

**ISP word 0** (`isp0`; base clear and triangle `0x01d00200`):

| bits | field | values | evidence |
|---|---|---|---|
| 7:0 | stencil reference | | **[CAP `stencil=always,85`]** → `0x55` |
| 8 | ISP word 2 present | | **[CAP `stencil=*`]**, with presence bit 2 |
| 9 | ISP word 1 present **[infer]** | 1 in every draw with `isp1` | |
| 17:15 | object type | 0 triangle, 1 line, 3 point | **[CAP `prim=lines`, `prim=points`]** |
| 20 | depth write off | | **[CAP `depthmask=0`]**; set when the depth test is off |
| 21 | colour write off | | **[CAP `mask=0000`]** |
| 24:22 | depth compare | GL order, 0 never … 7 always | **[CAP `depth=*`]**; 7 if off |
| 27:25 | pass type | 0 opaque, 1 blended, 3 scissor mask | **[CAP `blend=*`, `scissor=*`]** |

With the depth test on, the clear's word becomes `0x01c00200` (compare always, writes the
clear depth) and the triangle's `0x00400200` for `less`.

**ISP word 1** (`isp1`): the colour write mask, R G B A in bits 7, 6, 5, 4 **[CAP
`mask=1110`, `mask=1000`]**. Bit 12 is set for every compiled-shader draw and clear for the
clear (`0xf0`); its meaning is open.

**ISP word 2** (`isp2`, stencil) **[CAP `stencil=*`, `stencilmask=0f,f0`,
`stencilop=zero,incr,invert`, `stencilop=decr,incrwrap,decrwrap`]**:

| bits | field |
|---|---|
| 7:0 | write mask |
| 15:8 | compare mask (0 in the clear's word) |
| 18:16 | depth-pass operation |
| 21:19 | depth-fail operation |
| 24:22 | stencil-fail operation |
| 27:25 | stencil compare, GL order |

Operations: 0 keep, 1 zero, 2 replace, 3 increment (saturating), 4 decrement (saturating),
5 invert, 6 increment (wrapping), 7 decrement (wrapping). The clear writes `0x0e0200ff`
(always, replace, write mask `0xff`).

**Blending and colour masks are not fixed-function.** `blend=*` changes only the pass type
and the pixel shader: the compiled program combines its colour with the tile's current
`o0` (`sop2 … o0, pa0, o0`, with the factors and the add or subtract in the instruction);
`mask=1110` / `mask=1000` keep the pass type and end the shader with a byte-masked `sop2wm`
on `o0` besides the ISP write mask **[CAP]**. The fragment colour is a shader constant
(`color=*`): the secondary program DMAs it as f16 values or, for 0/1 components, the shader
builds it from immediates.

### S.4 Region clip, viewport, culling and the other MTE words

**Viewport** (`vp0`…`vp5`, floats): x offset, x scale, y offset, y scale, z offset, z scale
**[CAP `viewport=40,20,16,30`]** → 48, 8, 35, 15 and **[CAP `depthrange=0.25,0.75`]** → z
scale 0.25, offset 0.5. The y scale is positive: framebuffer row 0 is GL's bottom row
(consistent with the region clip below).

**Region clip** (`clip0`, `clip1`): bit 31 of word 0 on; first and last 32-pixel tile column
in word 0 (30:16, 15:0), first and last 16-pixel tile row in word 1 (31:16, 15:0) **[CAP
`size=*`, `scissor=40,20,16,30`]** → `0x80010001`, `0x00010003`. The clear always carries
the whole surface; a draw carries it only when a scissor or viewport is smaller than the
surface.

**Scissor and small viewports** are done with geometry: the driver inserts two ISP-only
draws (presence `0xd485`: no `isp1`, no pixel programs, no viewport; ISP word 0
`0x07e00100`: pass type 3, compare always, no colour or depth write) — a full-surface
rectangle with ISP word 2 = 0, then the scissor rectangle in pixels with ISP word 2 =
`0x02000000` — and then the draw with the region clip of that rectangle **[CAP
`scissor=*`, `viewport=*`]**. **[infer]** they build the ISP's per-pixel mask.

**MTE control** (`mtectl`; `0x01555620` for a draw, `0x40` for the screen-space draws):
bits 1:0 cull, 1 = counter-clockwise, 2 = clockwise triangles in the window coordinates the
viewport produces **[CAP `cull=back` → 2, `cull=front` and `cull=back frontface=cw` → 1;
`frontface=cw` alone changes nothing]**. `cull=both` makes the driver drop the draw. The
other bits never moved.

**End of scene** (`term`, in the kick-1 block `0x2000`): last 32 × 32 block column (31:16)
and row (15:0) **[CAP `size=*`]**: `0x00010001` for 64 × 64, `0x00030001` for 100 × 60.

**Output selects and coordinate words** (open, observations **[CAP]**): `outsel` 19:16 equals
the dwords the vertex task emits per vertex (4 for the triangle, 8 with `varying` and for the
clear, 7 for points, which add a size and two sprite coordinates); bit 8 is set for points;
bits 13:12 are 3 for compiled shaders, 1 (with bit 11) for the clear. `coordsize` /
`coordfmt` are 5 / 1 with `varying`, 5 / 0 for the clear, 2 / 1 for points and 0 / 0
otherwise.

### S.5 Pixel PDS pointers and the size word

The §9.3 inference holds: a pixel PDS pointer (`pds_sec`, `pds_pri`, the special object
words) is the data size in 16-byte rows (31:26) and the program offset from
`PDS_EXEC_BASE` >> 4 (23:0, only 16:0 used) **[CAP]**: in all 66 captures every pointer lands
on a PDSPIXEL program whose code, after that much data, ends in `halt`
(`test_state3d.py`). The size word between them: primary attribute rows (6:0, 1 in every
capture), 3 in 17:16 (the USE task size of the transfer queue's layout), secondary
attribute rows (24:18: 3 for the constant-colour shader, 0 for the clear and `varying`,
whose secondary is a no-op), and 31:25 = 11, 12 or 0 (open) **[CAP `varying`, `color=*`]**.

### S.6 TA and 3D registers

Across all 66 runs only these registers move **[CAP]**:

| register | layout | evidence |
|---|---|---|
| `te_screen` [DDK] | 32 × 16 tiles across − 1 (11:0), down − 1 (23:12) | `size=*` |

### S.8 Background object

The background object (`bg_obj_base_dev_addr`, 0x200 bytes) has the transfer queue's layout
(`sgx545_transfer.md` §4.2.3) with one TSP layer **[CAP]**: words 0–2 are the PDS pointers,
0 in the buffer and patched at render time (the special object words of the command hold
them, and the `hw_bg_obj_prim_pds_update_list_dev_addr` list holds the primary pointer
`0x0c00040e`); words 3–8 the texture coordinates (0, 0), (1, 0), (0, 1); word 9 zero; word 10
the vertex format `0x202` (one layer); words 15–22 the vertices (0, 0), (W, 0), (0, H) with
z = 1.0 in the 24.8 fixed-point format **[CAP `size=*`]**. `ISPBgObjTag = 0x02046400` (two
TSP dwords per vertex, the object at `BIF3DReqBase + 0x464000`), `ISPBgObjDepth` = 1.0 and
`ISPBgObj = 0x300` never change. Its primary program (`0xe40040e0`) starts the plain copy
shader (`o0 = pa0`) with an iterated coordinate (`douti`) and a texture fetch (`doutt`)
whose state holds the colour buffer address, `(W − 1) << 12 | (H − 1)` with a format byte
(`0xc5` RGB565, `0xcc` ARGB8888) and a stride-dependent word **[CAP `size=*`,
`format=8888`]**: the background object **reloads the previous colour buffer**. `glClear`
is not the background object: it is a screen-space triangle (0, 0), (2W, 0), (0, 2H) with
z = the clear depth and the colour packed as `0xAARRGGBB` in each vertex **[CAP `clear=*`,
`cleardepth=0.5`, `size=*`]**, and `noclear` simply leaves it out.

### S.9 What a minimal job needs, and what stays open

For one opaque, unclipped triangle the state is now fully determined: a state block with
presence `0xdf43` (ISP word 0 `0x01d00200`, ISP word 1 `0x10f0`, the two pixel pointers and
the size word, the viewport, `outsel`, `wclamp`, `mtectl`), the index list with its vertex
task, the end-of-scene block with `term`, the TEScreen/MTEScreen pair and the PBE words for
the surface. Open: the output-select and coordinate words beyond the observations above, the
rest of `mtectl`, ISP word 1 bit 12, the high bits of the pixel size word, the pass type 3
draws, two-sided stencil, the ZLS control word (no depth format variation yet), the
background reload's texture words and when the EDM runs that object.

## 14. First triangle [HW]

The kernel builds the §12.6 job with the §13 state and our own programs, kicks it and checks
the pixels (debugfs `dri/N/sgx/tri` and `tri2`; `kernel/gma500/sgxfive/sgx_tri.[ch]`, the
self-test in `sgxfive.c`). On the laptop it renders exactly, from the first run after boot,
in both kick forms and in two page-directory configurations, repeatably (20 runs in a row),
interleaved with transfers, and with the IGT suite and `sgxfive-test isolation` still
passing. Tested 2026-10-21 on the gma500 series patches 45 and 46.

### 14.1 The job

Everything is mapped at REV1 heap addresses (`sgx545_boot_sequence.md` (d)), in the EDM's
page directory unless stated:

| area | address | contents |
|---|---|---|
| 3D parameters | `0x10000000` | the heap base = `BIF_TA_REQ_BASE` = `BIF_3D_REQ_BASE` |
| | `+0x1000` | PB: `0x422` pages, as captured |
| | `+0x423000` | its page table, `0x40000` bytes, built by the host (§12.4) |
| | `+0x463000`, `+0x464000` | scratch primitive block; background object |
| TA data | `0x20001000` | a zeroed page each: tail pointers, DPM control, OTPM, DPM state, |
| | | region headers, ZLS region headers |
| kernel data | `0x32140000` | the TA client CCB (64 KiB + one command) |
| | `0x32152000` | CCB control, render context, RT data set, PB descriptor and block, |
| | | status words, render details |
| PDS vertex | `0x30401000` | vertex PDS, two state-copy PDS programs, the two MTE state blocks |
| vertex shader | `0x3c001000` | vertex shader and the two state-copy tasks (`USE_CODE_BASE_10`) |
| PDS pixel | `0x2e001000` | two colour primaries, the secondary, the pixel-event program |
| pixel shader | `0x37001000` | two colour shaders, secondary, PTOFF, end of tile, end of render |
| general | `0x3e001000` | the VDM streams, the vertices, the indices |
| | `0x3e010000` | the 64 × 64 ARGB8888 colour buffer and a guard page |

The structures are §12.6's with the captured values: render context flags `0x1` (new
context), RT data `CommonStatus` `0x10`, the 3D registers of §7 with `ISPBgObj` `0x300` and
`ISPIPFMisc` `0x000f0000`, `EDMPixelPDSExec` the absolute address of the pixel-event program
with `Data` 5 and `Info` 1, the TA registers of §6 with `TEScreen` `0x3001` and `MTEScreen`
`0x003f003f`, one TA and one 3D status word in the command as fences. The kernel CCB command is
`{0x11d, cache control, 0, render context}` with `INVAL_BIF_PT | _PD | INVAL_DATA`.

The VDM stream is 11 words: the state block of the triangle (PDS program, 2 data rows, 5
attribute rows), an index list of three 16-bit indices with the captured third and fourth
words (`0xf0000000`, `0x003fffff`) and its vertex task (partition size 15, a 4-dword vertex,
1 attribute row, 2 data rows), the end-of-scene state as the last task (`0x2000`,
`0x00010001`), and terminate. No secondary vertex state, no clear draw: the background object
paints every pixel the triangle does not cover. The MTE state block is the captured triangle's
(S.9): presence `0xdf43`, ISP words `0x01d00200` and `0x10f0`, our pixel pointers with size
word `0x00030001`, viewport 32, 32, 32, 32, 0.5, 0.5, output select `0x43000`, w clamp, MTE
control `0x01555620`, no iterated coordinates. The vertices are clip-space positions with
w = 1: (8, 8), (56, 20), (20, 56) in pixels, so x = px / 32 − 1.

### 14.2 The programs

All are our own source in `tools/usse-asm/progs/`, assembled into `sgx_tri_progs.h` by
`kernel/gen_tri_progs.py` (freshness test `kernel/test_gen_tri_progs.py`); `sgx_tri.c` patches
the per-placement words. Vertex side:

- `pds_vtx.s`: `mul ds1[50], ir0.l, stride`, `movsa doutd` of one 4-dword burst from the vertex
  buffer plus that offset, `(if0) movs doutu` of the shader (code base 10), `halt`.
- `use_vtx.s`: two phases. Phase 0 (`phas` to instruction 7, wait `vcull`) waits for the DMA
  (a predicated-off `ldad` and `wdf drc0`), copies `pa0`–`pa3` to `o0`–`o3` and ends with
  `emitvcbvtx.end.twopart`; phase 1 is `emitmtevtx.end.twopart.freep`. The `phas` operand is an
  instruction index from the code base, so the kernel adds the program's own index
  (`0x200` for `0x3c001000`).
- `pds_mte.s` + `use_mtest18.s` / `use_mtest2.s`: `doutd` the state block into the attributes
  (18 words as two lines of 9: `0x02000018`; the end of scene as one line of 2: `0x00400001`),
  then copy them to the outputs, `emitvcbst`, `wop`, `emitmtest.end.freep`.

Pixel side, reusing the transfer programs (`sgx545_transfer.md` §4.2.4): `pds_prim.s` +
`use_fill.s` for the triangle's colour and, as the background object's primary, for the
background colour; `pds_sec.s` + `use_sec.s` as the secondary of both; `pds_pixevent.s` with
its PTOFF case pointed at `use_ptoff.s` (`ptoff.end`), `use_eot.s` with the PBE words of the
64 × 64 surface (`0`, `0x003f003f`, `0x001f8000`, address, sideband `0x200`) and `use_eor.s`.

The assembler's encodings of the emits now follow the closed compiler's (an unprinted source
written as immediate 0, `tools/usse-asm/README.md`); the hardware was only run with those.

### 14.3 Results

- **Single kick** (flags `0x73`, render flags `0x400`, `TEPSG` `0x400000`): the 3D status word
  is written 150–330 µs after the kick, the TA status word too; the EDM advances the TA CCB
  read offset by `0x2c0`, drops `TACount` to 0, clears `READY` and `NEWCONTEXT`, sets
  `CommonStatus` back to `0x10` and the RT status word to 1, increments the RT data set's
  complete count, and clears `rtdata.hw_render_details_dev_addr` **[HW]**, as §12.2–§12.3 read.
  One or two `SW_EVENT` interrupts are counted: the TA's and the render's can arrive as one.
- **Two kicks** (the capture's: `0x71` with render flags 0 and the whole stream, then `0x62`
  with render flags `0x400`, `TEPSG` `0x400000` and a stream of the end-of-scene state and
  terminate): the same image; the RT data set's complete count goes up by 2 and the render
  details keep `TEState` `0x10000` from the first kick.
- **Pixels**: all 4096 are checked against a CPU reference that excludes a one-pixel band at
  each edge. 1062 triangle and 3034 background pixels, none wrong, the guard page untouched,
  and 612 mismatches if the reference is flipped in y: **memory row r is window y = r**, the
  viewport's positive y scale (S.4) puts clip-space y = −1 at the first row. The rendered
  area (1062) matches the triangle's 1080 within the edge band.
- **Empty tiles**: tiles the triangle does not touch get the background too (no sentinel
  left), with `ISPBgObj` `0x300` and without `ISPIPFMisc`'s process-empty bit: every tile of
  the region headers is rendered.
- **Page directories**: with `dri/N/sgx/tri_own_pd` the render context names a page directory
  of its own that maps the job and aliases every EDM buffer; the triangle renders the same, so
  the TA and 3D requestors follow the context's directory, as the transfer's 3D work does.
- After the renders `DPM_3D_FREE_LIST` reads `0x04220003` and the PB descriptor's free list
  `0x04220001`/`0x04210000` again: the scene's two pages were freed by the render.

A failure mode seen on the way, for debugging the next jobs: a render context address the
EDM cannot reach (here 0x100, from an uninitialised CCB command) makes the EDM fault at page 0
(`BIF_INT_STAT` `0x000d0400`, `BIF_FAULT` `0x0000000f`) after reading the kernel CCB command,
with no `SW_EVENT`, the context untouched (`TACount` 0, `NEWCONTEXT` still set) and the pipe
stalled until a reset. The same signature as the stale-BIF faults of
`sgx545_render_uapi.md`, so a page-0 fault means "check the addresses" first.
