# SGX545 3D — what the GLES2 stack submits for one triangle (draft)

First draft of the 3D design note (plan step 3 starts here). It records what the closed
Cedarview GLES2 stack (DDK 1.7.862890) submits to draw one constant-colour triangle into a
64×64 RGB565 pbuffer, as captured by the harness (`harness/ukernel-extract/README.md`,
"3D capture"), with the structures decoded by `kick3d.py` and `summary3d.py`. The aim is the
minimal TA + 3D job a kernel self-test can build from our own programs (plan step 4).

Conventions:

- Tags as in the other design documents: **[DDK]** GPL DDK source, **[CAP]** captured from the
  closed userspace under the harness, **[RE]** read from closed-binary disassembly, **[infer]**
  inference, to verify before relying on it. **[PSP2]** marks layouts and field names read
  from the DDK 1.8 client headers in `reference/PVR_PSP2` (`reference/CATALOG.md` §7): facts
  only, with every SGX545 conditional member pinned by a captured structure size.
- `CDV` is Intel's GPL Cedarview kernel patch, `DDK` the GPL `reference/sgx545-ce` tree (the
  first, verbatim commit). Device addresses are the harness layout (heap bases of
  `sgxconfig.h`, first object at heap base + `0x1000`); objects are page-aligned and never
  reused, so addresses are stable between runs but not those of a real driver.
- "obj N" is the harness object index in the capture (`extracted/gles2_tri/MANIFEST.md`).

## 1. How it was captured

The closed stack ran on the build host as i686 code under `fakedrm.so` (an `LD_PRELOAD`
libdrm). Nothing in the stack needed patching **[CAP]**:

- **Window system.** libIMGegl loads the WSEGL module named by the `WindowSystem` app hint
  from `/etc/powervr.ini` (default `libpvrPVR2D_DRIWSEGL.so`) and takes its function table
  from `WSEGL_GetFunctionTablePointer`. The closed modules export interface version 2: a
  version word and 14 entry points **[RE]**. Our `fakewsegl.c` offers one RGB565 config and no
  native drawables; `eglCreatePbufferSurface` never calls into it, so a pbuffer needs no
  display, no libpvr2d and no display-class device.
- **Kernel answers.** The client path needs the heap list (11 heaps including SYNCINFO
  `0xE0000000` and the per-context parameter heap `0xC0000000`), allocations with sync objects,
  `SGX_GETCLIENTINFO` (the `asInitDevData` srvinit gave the kernel), `SGX_GETMISCINFO`
  `DRIVER_SGXREV` (DDK version `0x010711`, build 862890, build options `0x60218`; with
  zeros `eglInitialize` fails with `EGL_BAD_ALLOC`), the global event object, the host
  control block, and the HW render and transfer context registrations.
- **ABI details pinned by the run.** `ALLOC_DEVICEMEM`'s OUT is 19 dwords: `sCpuPAddr` is
  32-bit, the sync info is the last five dwords, and the client maps a buffer by passing its
  **kernel** handle (`hKernelMemInfo`, `hKernelSyncInfo`) to `MHANDLE_TO_MMAP_DATA` **[CAP]**.
  `SGX_DOKICK`'s IN is 564 bytes, which matches `SGX_CCB_KICK` with
  `SUPPORT_SGX_NEW_STATUS_VALS` on and generalised sync objects off, the CDV configuration
  **[DDK/CAP]**.
- **Kernel and EDM emulation.** At each kick the shim performs `SGXDoKickKM`'s writes to the
  client CCB (§4.2), snapshots every object, then writes the status values and bumps the sync
  complete counters as the EDM would, so `glFinish` returns.

## 2. The call sequence

- **`eglInitialize`**: connect, enumerate, `SGX_GETMISCINFO`, memory context, client info,
  misc info, global event object, internal dev info, 70 allocations, HW render and transfer
  context registration. 72 objects: PB, render context, TA CCB, and the transfer queue with
  52 small pixel-shader buffers, its built-in programs **[infer]**.
- **`eglCreatePbufferSurface`**: 40 allocations: colour buffer, three render details, RT data
  set, TADATA buffers, background object, end-of-render PDS buffer.
- **`eglCreateContext`**: 21 allocations: vertex and index buffers, VDM stream, USSE and PDS
  circular buffers, status words.
- **Shaders, `glClear`, `glDrawArrays`**: no bridge calls but two allocations in the draw.
- **`glFinish`**: two `SGX_DOKICK`s.
- **`eglTerminate`**: flush render target, 17 sync-token waits, unregister both contexts,
  free everything.

No `SGX_FINDSHAREDPBDESC` / `ADDSHAREDPBDESC`: the build uses `SUPPORT_PERCONTEXT_PB`
(CDV `Makefile`) **[DDK]**, so the client allocates its parameter buffer itself **[CAP]**.
Shader compilation is CPU-only; the programs are copied into circular buffers at draw time.

## 4. The kick

### 4.1 HW render context — `SGXMKIF_HWRENDERCONTEXT`, `0x44` [PSP2/CAP]

Registered once with `SGX_REGISTER_HW_RENDER_CONTEXT` (`SGX_CMD_BASE + 20`): the kernel copies
the client image into KERNEL_DATA and writes the page-directory address at offset 8, exactly
as for the transfer context **[DDK]**. Captured: flags `0x21` (new context, per-context PB),
priority 0, `ta_ccb_base_dev_addr` / `ta_ccb_ctl_dev_addr` (the TA client CCB and its control),
`sHWPBDescDevVAddr`, `scratch_prim_block` (`0x40` bytes in the parameter heap), four list heads
and four list links for partial / complete renders, all 0, and the PID at `+0x40`.

### 4.2 `SGX_CCB_KICK` and the kernel's part [DDK/CAP]

`SGX_DOKICK` (`SGX_CMD_BASE + 3`) carries the kernel CCB command and the sync/status lists.
In both kicks: `sCommand.ui32Data[1]` = the HW render context, all other command words 0
(the kernel fills `ui32ServiceAddress` with the TA handler `0x11d` and the cache control);
`hCCBKernelMemInfo` = the TA client CCB; one destination sync (the colour buffer's), 7 TA and
3 3D status updates; `ui32CCBOffset` = the command's shared block (`+0x58`).

`sgxkick.c:SGXDoKickKM` then writes, inside the client CCB, the shared block
`SGXMKIF_CMDTA_SHARED` (`0x1e0`): the TA/3D TQ sync values and addresses for `hTASyncInfo` /
`h3DSyncInfo`, the source syncs, the TA→3D dependency, copies of the status updates, and
finally `ui32CtrlFlags |= READY` (`0x1`). On the first kick of a scene with destination syncs
it fills the HW destination sync list (`{sAccessDevAddr, count, PVRSRV_DEVICE_SYNC_OBJECT[]}`)
from the kernel sync infos and bumps their write-ops pending. It never touches the rest of the
command. So a kernel that builds the job itself writes the whole `SGXMKIF_CMDTA` and queues a
kernel CCB command `{0x11d, cache control, 0, render context, 0, 0, 0, 0}` **[DDK/infer]**.

### 4.3 Two kicks per frame [CAP]

| | kick 0 | kick 1 |
|---|---|---|
| CMDTA in CCB | `+0x0` | `+0x2c0` |
| `ui32Flags` | `0x71`: first kick, invalidate USE/PDS/data caches | `0x62`: last kick, PDS/data |
| `render_flags` | 0 | `0x400`: render scene |
| VDM stream | `0x0808c000`: clear + triangle | `0x0808c05c`: end of scene |
| `h3DSyncInfo` | none | the pbuffer surface's sync (3D TQ fields filled) |
| TA status [0], [6] | `0x5c`, 1 | `0x70`, 2 |

`glFinish` first flushes the recorded geometry as a TA-only kick, then terminates the scene
with a second, tiny TA kick that asks for the render. Both use the same render details,
RT data and PB.

## 5. Parameter buffer [PSP2/CAP]

`hw_pb_desc` (`0x3c`): flags 0, `ui32NumPages = 0x422`, free list initial head/tail
`0x04220001`, previous `0x04210000`, `evm_page_table_dev_vaddr = 0xc0423000`, current free list
equal to the initial one, thresholds TA `0x432`, ZLS `0x400`, global `0x400`, PDS `0x300`,
`list_pb_block_dev_vaddr` = one `hw_pb_block` {`0x422` pages, head/tail `0x04220001`,
parent = the descriptor}. The command carries its own threshold update block (all 0 here).
`BIFTAReqBase` and `BIF3DReqBase` are both `0xc0000000`, the parameter heap base. The free list
words look like {tail, head} page indices in two 16-bit halves **[infer]**; the EDM initialises
the DPM page table from them (the PB descriptor's page-table-init flag is clear in the
capture, so the EDM or the client did it earlier) **[infer]**.

## 6. The TA command — `SGXMKIF_CMDTA`, `0x2b0` + register updates [PSP2/CAP]

Header (22 dwords): `ui32Size = 0x2c0`, `ui32Flags`, `spec_object = {0x04001800,
0x00030001, 0x0c00040e}` (special/background object words; the first is a pixel PDS reference,
§9.3), vertex partitions `0x50000000` (both), `render_flags`, frame number,
`sHWPBDescDevVAddr`, a 4-dword PB threshold update, the render details, destination sync list,
RT data set and current RT data (`rt_data[1]`, `+0x50` in the set), visibility results, Z/S
buffer strides and `num_3d_regs = 0`. Then the shared block (§4.2), then the TA registers:

| field | value | meaning |

| `teaa` | `0x20000000` | TE anti-aliasing mode |
| `te_mtile_1` / `2` | `0x01004004` | macrotile layout |
| `te_screen` | `0x3001` | screen in tiles **[infer]** |
| `te_mtile_stride` | `0x10` | |
| `te_psg` | 0 / `0x400000` | kick 1 sets one bit (end of scene) **[infer]** |
| `vdm_ctrl_stream_base` | `0x0808c000` / `0x0808c05c` | VDM stream of this kick |
| `mte_ctrl` | `0xa2` | |

The GSG, complex-geometry, ITP and render-target-array words are 0.

## 8. Render target data [PSP2/CAP]

`hw_rt_data_set` (`0x18` header): pending-count word, complete count, `mtile_width = 8`,
out-of-memory and SPM counters, `num_rt_data = 2`, then two `hw_rt_data` (`0x38`) for
TA/3D overlap. Each has the render context, `num_tile_blocks_per_mt = 1`,
`mt_region_array_size = 0xc0`, the background object (`0xc0464000`, shared), a DPM context
state of its own (`0xd0005000`, `0xd0007000`), shared DPM context control (`0xd0002000`,
`0x40`), OTPM (`0xd0003000`, `0x50`), tail pointers (`0xd0001000`, `0x100`, `tail_size`),
one RT in the array, an RT status word of its own, and `common_status = 0x10`. The
background object holds 1.0 floats and small words: its PDS/ISP layout is open.

## 9. The VDM stream and the programs

### 9.1 VDM control stream [PSP2/CAP]

Every block starts with a type in bits 31:30: link, state, index list, terminate. A state
block is two words: the PDS program address >> 4 in bits 27:0 with a last-task flag (29) and a
complex-geometry flag (28), then, for the plain form, the PDS data size in 16-byte rows
(31:26), SD (25), fence (18), MTE emit (17), USE pipe (15:13), partial (12), partitions
(11:9), secondary (8) and the USE attribute size in 16-byte rows (7:0). An index-list header
holds the primitive type (29:26), presence bits for a third and fourth word (22, 23) and the
index count (21:0); its second word is the index buffer address. Kick 0's stream:

| word | block | decoded |
|---|---|---|
| 0 | state | PDS `0xec011000`, 3 rows of data, MTE emit: copy the clear's MTE state |
| 2 | index list | triangles, 3 indices at `0x080c3000` (16-bit 0, 1, 2): the clear |
| 6 | state, complex, last task | PDS `0xec003040`: the clear's vertex task |
| 8 | state | PDS `0xec011080`: copy the triangle's MTE state |
| 10 | state, secondary | PDS `0xec003120`: secondary (constant) task for the triangle |
| 12 | index list | triangles, 3 indices at `0x080f5000` (0, 1, 2 …): the draw |
| 16 | type 3, complex, last task | PDS `0xec01e000`: the triangle's vertex task; ends kick 0 |

Kick 1's stream (`+0x5c`): a secondary state (PDS `0xec002000`, a no-op USSE task), a
last-task state (PDS `0xec001000`, an MTE state copy of two words), and a plain terminate.
The vertex task of each draw follows its index list as a complex-form state; the complex form
of the second word (here `0x02c00082`, `0x01c00082`) is not decoded yet **[CAP/infer]**.

### 9.2 Vertex side [CAP/RE]

PDS programs are a data segment of 4-dword rows (`ds0[2r]`, `ds0[2r+1]`, `ds1[2r]`,
`ds1[2r+1]`) followed by code (spec §13.8). A USSE code-address word holds a
`EUR_CR_USE_CODE_BASE` index in bits 3:0 and an instruction index from that base above it;
srvinit programs bases 0–9 for pixel code (`0xf4000000` + n × `0x80000`), 10–13 for vertex code
(`0xfc000000` …) and 15 for the EDM **[CAP]**. The clear's words use base 10 (`0x0001010a` →
`0xfc008080`).

- **MTE state copy** (PDS `0xec011000`, `0xec011080`): `doutd` DMAs a state block from the
  PDS vertex heap (`0xec003000` / `0xec003080`; control words `0x02c0000b` / `0x02000018`, whose
  low bits look like a dword count **[infer]**) and `doutu` starts a USSE task
  (`0xfc008700`, `0xfc008a00`) that loads the block and writes it out (`mov.repeat12` /
  `repeat16` + `repeat2` to `o`, then `emitvcbst` and `emitmtest`).
- **Clear vertex task** (PDS `0xec003040`): DMA from `0x08091000` (the clear's three vertices,
  `{x, y, z = 1.0, colour 0xff0000ff}` in screen pixels: (0, 0), (128, 0), (0, 128), a triangle
  covering the 64×64 target) and USSE `0xfc008080`: copy x, y, z, set w = 1.0 from a
  constant, unpack the four colour bytes to floats, `emitvcbvtx`, `emitmtevtx`.
- **Triangle vertex task** (PDS `0xec01e000`): DMA from `0x08091030` (our three vertices,
  `{±0.5, -0.5 / 0.5, 0, 1}`) and USSE `0xfc008d80`: two phases, `ldad.fetch4` the position,
  copy it to `o0..o3`, `emitvcbvtx`, `emitmtevtx` — the compiled `gl_Position = pos`.
- **Secondary task** (PDS `0xec003120`): DMA a block from `0xec0030e0` (control
  `0x02400009`; it holds the floats `2/255`, `1/255`, `1/32767`, `1/65535`, unpacking scales
  **[infer]**) and a one-instruction USSE no-op (`phas.end`).

### 9.3 Pixel side [CAP/RE/infer]

The MTE state blocks reference pixel PDS programs with words holding the data size in 16-byte
rows (31:26) and the program offset from `PDS_EXEC_BASE` (`0xe4000000`) >> 4 in the low bits
**[infer]**: three references decode to programs whose data size matches exactly. In each
state block, word 3 is the secondary program and word 5 the primary one.

- **Clear**: secondary `0x04001800` → `0xe4018000` (USSE `phas.end`, nothing to do); primary
  `0x08000412` → `0xe4004120`: `doutu` USSE `0xf4038170` (`mov.end o0, pa0`) and `douti`
  (iterate the vertex colour into `pa0`). The background object words use the same
  `0x04001800`.
- **Triangle**: secondary `0x0800041a` → `0xe40041a0`: `doutd` the four f16 colour components
  `{1.0, 0.5, 0.25, 1.0}` (at `0xe4004184`) into attribute registers and run USSE `0xf4038300`,
  which packs them to 8-bit (`pcku8f16`) into `pa9`; primary `0x04001802` → `0xe4018020`:
  USSE `0xf4038380`, `mov.end o0, sa9` — the compiled `gl_FragColor = vec4(1, .5, .25, 1)`.

Other state words (`0x0000d4c3`/`0x0000df43`, `0x01d00200`, `0x000000f0`/`0x000010f0`,
`0x00030001`/`0x160f0001`, the viewport scale/offset `32.0, 32.0, 32.0, 32.0, 0.5, 0.5`, …) are
the MTE/ISP/TSP state; not decoded yet.

### 9.4 End of render [CAP/RE]

`EDMPixelPDSExec = 0xe4004000` with `Data = 5` (rows of four dwords: 20 data dwords) and
`Info = 1`. The program tests the event bits in `ir1` against masks in its data and starts
one of three USSE tasks:

- `0xf4035000` (address word `0x0106a000`): **end of tile**. It loads `r0 = 0`,
  `r1 = 0x003f003f` (63, 63), `r2 = 0x001f8000`, `r3 = 0x08087000` — the colour buffer — and
  emits them to the pixel back end with `emitpix1` / `emitpix2.end`. These are the PBE state
  words for a 64×64 RGB565 target; their bitfields are open.
- `0xf4038200`: `ptoff.end`, and `0xf4038280`: `emitpix2.end` with zeros (other events,
  **[infer]** end of render and flush).

## 10. Completion [DDK/CAP/infer]

Each kick carries 7 TA and 3 3D status updates (`{address, value}`, copied into the shared
block). The TA ones are the client's circular-buffer read offsets and a kick counter
(e.g. `*0xe0019000 = 0x5c` then `0x70`, `*0xe0017000 = 1` then 2); the 3D ones are the
fragment buffers' offsets and a render counter. The EDM writes them when the TA (resp. the
render) is done; the client waits on them before reusing buffer space and on the colour
buffer's sync (write-ops complete) for `glFinish`. With the shim writing them at the kick, the
client never waits.

## 11. Open questions (steps 3 and 4)

1. **Complex-form state** (the vertex tasks): the layout of the second word, where the PDS
   data size lives, and whether the type-3 block at the end of kick 0 is a terminate that also
   runs a vertex task.
2. **MTE / ISP / TSP state words** in the state blocks, and the pixel PDS reference encoding
   (§9.3 is an inference from three samples): needs captures with different state (depth
   test, blending, other colours and sizes) to correlate.
3. **PBE words** of the end-of-tile program (`r0..r3`): format, stride, tile extents.
4. **Background object** (`0xc0464000`, the special object words, `ISPBgObj*`) and how the
   clear interacts with it: the clear is drawn as geometry here.
5. **3D register bitfields** (`TEAA`, `MTECtrl`, `ISPIPFMisc`, `TSPConfig`, `PixelBE`, …):
   correlate with the EDM's register writes (spec §13.6) and differential captures.
6. **PB initialisation**: who builds the DPM page table and free list (the descriptor's
   init-page-table flag is clear at the first kick), and the threshold semantics.
7. **The EDM's TA and 3D paths** (`edm.ta` at `0x11d`): which command fields it loads into
   which registers, to confirm the layouts above against the microkernel.
8. **Minimal job for step 4**: drop the transfer context, use one RT data, no secondary
   programs (constant colour in the primary pixel program), our own PDS/USSE programs from
   `usse-asm`, and a kernel-built `SGXMKIF_CMDTA` with one TA kick that also terminates the
   scene.
