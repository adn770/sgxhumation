# SGX545 3D — what the GLES2 stack submits for one triangle (draft)

First draft of the 3D design note (plan step 3 starts here). It records what the closed
Cedarview GLES2 stack (DDK 1.7.862890) submits to draw one constant-colour triangle into a
64×64 RGB565 pbuffer, as captured by the harness (`harness/ukernel-extract/README.md`,
"3D capture"), with the structures decoded by `kick3d.py` and `summary3d.py`. The aim is the
minimal TA + 3D job a kernel self-test can build from our own programs (plan step 4).

Conventions:

- Tags as in the other design documents: **[DDK]** GPL DDK source, **[CAP]** captured from the
  closed userspace under the harness, **[RE]** read from closed-binary disassembly, **[infer]**
  inference, to verify before relying on it. **[PSP2]** marks layouts and field names read
  from the DDK 1.8 client headers in `reference/PVR_PSP2` (`reference/CATALOG.md` §7): facts
  only, with every SGX545 conditional member pinned by a captured structure size.
- `CDV` is Intel's GPL Cedarview kernel patch, `DDK` the GPL `reference/sgx545-ce` tree (the
  first, verbatim commit). Device addresses are the harness layout (heap bases of
  `sgxconfig.h`, first object at heap base + `0x1000`); objects are page-aligned and never
  reused, so addresses are stable between runs but not those of a real driver.
- "obj N" is the harness object index in the capture (`extracted/gles2_tri/MANIFEST.md`).

## 1. How it was captured

The closed stack ran on the build host as i686 code under `fakedrm.so` (an `LD_PRELOAD`
libdrm). Nothing in the stack needed patching **[CAP]**:

- **Window system.** libIMGegl loads the WSEGL module named by the `WindowSystem` app hint
  from `/etc/powervr.ini` (default `libpvrPVR2D_DRIWSEGL.so`) and takes its function table
  from `WSEGL_GetFunctionTablePointer`. The closed modules export interface version 2: a
  version word and 14 entry points **[RE]**. Our `fakewsegl.c` offers one RGB565 config and no
  native drawables; `eglCreatePbufferSurface` never calls into it, so a pbuffer needs no
  display, no libpvr2d and no display-class device.
- **Kernel answers.** The client path needs the heap list (11 heaps including SYNCINFO
  `0xE0000000` and the per-context parameter heap `0xC0000000`), allocations with sync objects,
  `SGX_GETCLIENTINFO` (the `asInitDevData` srvinit gave the kernel), `SGX_GETMISCINFO`
  `DRIVER_SGXREV` (DDK version `0x010711`, build 862890, build options `0x60218`; with
  zeros `eglInitialize` fails with `EGL_BAD_ALLOC`), the global event object, the host
  control block, and the HW render and transfer context registrations.
- **ABI details pinned by the run.** `ALLOC_DEVICEMEM`'s OUT is 19 dwords: `sCpuPAddr` is
  32-bit, the sync info is the last five dwords, and the client maps a buffer by passing its
  **kernel** handle (`hKernelMemInfo`, `hKernelSyncInfo`) to `MHANDLE_TO_MMAP_DATA` **[CAP]**.
  `SGX_DOKICK`'s IN is 564 bytes, which matches `SGX_CCB_KICK` with
  `SUPPORT_SGX_NEW_STATUS_VALS` on and generalised sync objects off, the CDV configuration
  **[DDK/CAP]**.
- **Kernel and EDM emulation.** At each kick the shim performs `SGXDoKickKM`'s writes to the
  client CCB (§4.2), snapshots every object, then writes the status values and bumps the sync
  complete counters as the EDM would, so `glFinish` returns.

## 2. The call sequence

- **`eglInitialize`**: connect, enumerate, `SGX_GETMISCINFO`, memory context, client info,
  misc info, global event object, internal dev info, 70 allocations, HW render and transfer
  context registration. 72 objects: PB, render context, TA CCB, and the transfer queue with
  52 small pixel-shader buffers, its built-in programs **[infer]**.
- **`eglCreatePbufferSurface`**: 40 allocations: colour buffer, three render details, RT data
  set, TADATA buffers, background object, end-of-render PDS buffer.
- **`eglCreateContext`**: 21 allocations: vertex and index buffers, VDM stream, USSE and PDS
  circular buffers, status words.
- **Shaders, `glClear`, `glDrawArrays`**: no bridge calls but two allocations in the draw.
- **`glFinish`**: two `SGX_DOKICK`s.
- **`eglTerminate`**: flush render target, 17 sync-token waits, unregister both contexts,
  free everything.

No `SGX_FINDSHAREDPBDESC` / `ADDSHAREDPBDESC`: the build uses `SUPPORT_PERCONTEXT_PB`
(CDV `Makefile`) **[DDK]**, so the client allocates its parameter buffer itself **[CAP]**.
Shader compilation is CPU-only; the programs are copied into circular buffers at draw time.

## 4. The kick

### 4.1 HW render context — `SGXMKIF_HWRENDERCONTEXT`, `0x44` [PSP2/CAP]

Registered once with `SGX_REGISTER_HW_RENDER_CONTEXT` (`SGX_CMD_BASE + 20`): the kernel copies
the client image into KERNEL_DATA and writes the page-directory address at offset 8, exactly
as for the transfer context **[DDK]**. Captured: flags `0x21` (new context, per-context PB),
priority 0, `ta_ccb_base_dev_addr` / `ta_ccb_ctl_dev_addr` (the TA client CCB and its control),
`sHWPBDescDevVAddr`, `scratch_prim_block` (`0x40` bytes in the parameter heap), four list heads
and four list links for partial / complete renders, all 0, and the PID at `+0x40`.

### 4.2 `SGX_CCB_KICK` and the kernel's part [DDK/CAP]

`SGX_DOKICK` (`SGX_CMD_BASE + 3`) carries the kernel CCB command and the sync/status lists.
In both kicks: `sCommand.ui32Data[1]` = the HW render context, all other command words 0
(the kernel fills `ui32ServiceAddress` with the TA handler `0x11d` and the cache control);
`hCCBKernelMemInfo` = the TA client CCB; one destination sync (the colour buffer's), 7 TA and
3 3D status updates; `ui32CCBOffset` = the command's shared block (`+0x58`).

`sgxkick.c:SGXDoKickKM` then writes, inside the client CCB, the shared block
`SGXMKIF_CMDTA_SHARED` (`0x1e0`): the TA/3D TQ sync values and addresses for `hTASyncInfo` /
`h3DSyncInfo`, the source syncs, the TA→3D dependency, copies of the status updates, and
finally `ui32CtrlFlags |= READY` (`0x1`). On the first kick of a scene with destination syncs
it fills the HW destination sync list (`{sAccessDevAddr, count, PVRSRV_DEVICE_SYNC_OBJECT[]}`)
from the kernel sync infos and bumps their write-ops pending. It never touches the rest of the
command. So a kernel that builds the job itself writes the whole `SGXMKIF_CMDTA` and queues a
kernel CCB command `{0x11d, cache control, 0, render context, 0, 0, 0, 0}` **[DDK/infer]**.

### 4.3 Two kicks per frame [CAP]

| | kick 0 | kick 1 |
|---|---|---|
| CMDTA in CCB | `+0x0` | `+0x2c0` |
| `ui32Flags` | `0x71`: first kick, invalidate USE/PDS/data caches | `0x62`: last kick, PDS/data |
| `render_flags` | 0 | `0x400`: render scene |
| VDM stream | `0x0808c000`: clear + triangle | `0x0808c05c`: end of scene |
| `h3DSyncInfo` | none | the pbuffer surface's sync (3D TQ fields filled) |
| TA status [0], [6] | `0x5c`, 1 | `0x70`, 2 |

`glFinish` first flushes the recorded geometry as a TA-only kick, then terminates the scene
with a second, tiny TA kick that asks for the render. Both use the same render details,
RT data and PB.

## 5. Parameter buffer [PSP2/CAP]

`hw_pb_desc` (`0x3c`): flags 0, `ui32NumPages = 0x422`, free list initial head/tail
`0x04220001`, previous `0x04210000`, `evm_page_table_dev_vaddr = 0xc0423000`, current free list
equal to the initial one, thresholds TA `0x432`, ZLS `0x400`, global `0x400`, PDS `0x300`,
`list_pb_block_dev_vaddr` = one `hw_pb_block` {`0x422` pages, head/tail `0x04220001`,
parent = the descriptor}. The command carries its own threshold update block (all 0 here).
`BIFTAReqBase` and `BIF3DReqBase` are both `0xc0000000`, the parameter heap base. The free list
words look like {tail, head} page indices in two 16-bit halves **[infer]**; the EDM initialises
the DPM page table from them (the PB descriptor's page-table-init flag is clear in the
capture, so the EDM or the client did it earlier) **[infer]**.

| `te_screen` | `0x3001` | screen in tiles **[infer]** |
| `te_mtile_stride` | `0x10` | |
| `te_psg` | 0 / `0x400000` | kick 1 sets one bit (end of scene) **[infer]** |

## 8. Render target data [PSP2/CAP]

`hw_rt_data_set` (`0x18` header): pending-count word, complete count, `mtile_width = 8`,
out-of-memory and SPM counters, `num_rt_data = 2`, then two `hw_rt_data` (`0x38`) for
TA/3D overlap. Each has the render context, `num_tile_blocks_per_mt = 1`,
`mt_region_array_size = 0xc0`, the background object (`0xc0464000`, shared), a DPM context
state of its own (`0xd0005000`, `0xd0007000`), shared DPM context control (`0xd0002000`,
`0x40`), OTPM (`0xd0003000`, `0x50`), tail pointers (`0xd0001000`, `0x100`, `tail_size`),
one RT in the array, an RT status word of its own, and `common_status = 0x10`. The
background object holds 1.0 floats and small words: its PDS/ISP layout is open.

## 9. The VDM stream and the programs

### 9.1 VDM control stream [PSP2/CAP]

Every block starts with a type in bits 31:30: link, state, index list, terminate. A state
block is two words: the PDS program address >> 4 in bits 27:0 with a last-task flag (29) and a
complex-geometry flag (28), then, for the plain form, the PDS data size in 16-byte rows
(31:26), SD (25), fence (18), MTE emit (17), USE pipe (15:13), partial (12), partitions
(11:9), secondary (8) and the USE attribute size in 16-byte rows (7:0). An index-list header
holds the primitive type (29:26), presence bits for a third and fourth word (22, 23) and the
index count (21:0); its second word is the index buffer address. Kick 0's stream:

| word | block | decoded |
|---|---|---|
| 0 | state | PDS `0xec011000`, 3 rows of data, MTE emit: copy the clear's MTE state |
| 2 | index list | triangles, 3 indices at `0x080c3000` (16-bit 0, 1, 2): the clear |
| 6 | state, complex, last task | PDS `0xec003040`: the clear's vertex task |
| 8 | state | PDS `0xec011080`: copy the triangle's MTE state |
| 10 | state, secondary | PDS `0xec003120`: secondary (constant) task for the triangle |
| 12 | index list | triangles, 3 indices at `0x080f5000` (0, 1, 2 …): the draw |
| 16 | type 3, complex, last task | PDS `0xec01e000`: the triangle's vertex task; ends kick 0 |

Kick 1's stream (`+0x5c`): a secondary state (PDS `0xec002000`, a no-op USSE task), a
last-task state (PDS `0xec001000`, an MTE state copy of two words), and a plain terminate.
The vertex task of each draw follows its index list as a complex-form state; the complex form
of the second word (here `0x02c00082`, `0x01c00082`) is not decoded yet **[CAP/infer]**.

### 9.2 Vertex side [CAP/RE]

PDS programs are a data segment of 4-dword rows (`ds0[2r]`, `ds0[2r+1]`, `ds1[2r]`,
`ds1[2r+1]`) followed by code (spec §13.8). A USSE code-address word holds a
`EUR_CR_USE_CODE_BASE` index in bits 3:0 and an instruction index from that base above it;
srvinit programs bases 0–9 for pixel code (`0xf4000000` + n × `0x80000`), 10–13 for vertex code
(`0xfc000000` …) and 15 for the EDM **[CAP]**. The clear's words use base 10 (`0x0001010a` →
`0xfc008080`).

- **MTE state copy** (PDS `0xec011000`, `0xec011080`): `doutd` DMAs a state block from the
  PDS vertex heap (`0xec003000` / `0xec003080`; control words `0x02c0000b` / `0x02000018`, whose
  low bits look like a dword count **[infer]**) and `doutu` starts a USSE task
  (`0xfc008700`, `0xfc008a00`) that loads the block and writes it out (`mov.repeat12` /
  `repeat16` + `repeat2` to `o`, then `emitvcbst` and `emitmtest`).
- **Clear vertex task** (PDS `0xec003040`): DMA from `0x08091000` (the clear's three vertices,
  `{x, y, z = 1.0, colour 0xff0000ff}` in screen pixels: (0, 0), (128, 0), (0, 128), a triangle
  covering the 64×64 target) and USSE `0xfc008080`: copy x, y, z, set w = 1.0 from a
  constant, unpack the four colour bytes to floats, `emitvcbvtx`, `emitmtevtx`.
- **Triangle vertex task** (PDS `0xec01e000`): DMA from `0x08091030` (our three vertices,
  `{±0.5, -0.5 / 0.5, 0, 1}`) and USSE `0xfc008d80`: two phases, `ldad.fetch4` the position,
  copy it to `o0..o3`, `emitvcbvtx`, `emitmtevtx` — the compiled `gl_Position = pos`.
- **Secondary task** (PDS `0xec003120`): DMA a block from `0xec0030e0` (control
  `0x02400009`; it holds the floats `2/255`, `1/255`, `1/32767`, `1/65535`, unpacking scales
  **[infer]**) and a one-instruction USSE no-op (`phas.end`).

### 9.3 Pixel side [CAP/RE/infer]

The MTE state blocks reference pixel PDS programs with words holding the data size in 16-byte
rows (31:26) and the program offset from `PDS_EXEC_BASE` (`0xe4000000`) >> 4 in the low bits
**[infer]**: three references decode to programs whose data size matches exactly. In each
state block, word 3 is the secondary program and word 5 the primary one.

- **Clear**: secondary `0x04001800` → `0xe4018000` (USSE `phas.end`, nothing to do); primary
  `0x08000412` → `0xe4004120`: `doutu` USSE `0xf4038170` (`mov.end o0, pa0`) and `douti`
  (iterate the vertex colour into `pa0`). The background object words use the same
  `0x04001800`.
- **Triangle**: secondary `0x0800041a` → `0xe40041a0`: `doutd` the four f16 colour components
  `{1.0, 0.5, 0.25, 1.0}` (at `0xe4004184`) into attribute registers and run USSE `0xf4038300`,
  which packs them to 8-bit (`pcku8f16`) into `pa9`; primary `0x04001802` → `0xe4018020`:
  USSE `0xf4038380`, `mov.end o0, sa9` — the compiled `gl_FragColor = vec4(1, .5, .25, 1)`.

Other state words (`0x0000d4c3`/`0x0000df43`, `0x01d00200`, `0x000000f0`/`0x000010f0`,
`0x00030001`/`0x160f0001`, the viewport scale/offset `32.0, 32.0, 32.0, 32.0, 0.5, 0.5`, …) are
the MTE/ISP/TSP state; not decoded yet.

### 9.4 End of render [CAP/RE]

`EDMPixelPDSExec = 0xe4004000` with `Data = 5` (rows of four dwords: 20 data dwords) and
`Info = 1`. The program tests the event bits in `ir1` against masks in its data and starts
one of three USSE tasks:

- `0xf4035000` (address word `0x0106a000`): **end of tile**. It loads `r0 = 0`,
  `r1 = 0x003f003f` (63, 63), `r2 = 0x001f8000`, `r3 = 0x08087000` — the colour buffer — and
  emits them to the pixel back end with `emitpix1` / `emitpix2.end`. These are the PBE state
  words for a 64×64 RGB565 target; their bitfields are open.
- `0xf4038200`: `ptoff.end`, and `0xf4038280`: `emitpix2.end` with zeros (other events,
  **[infer]** end of render and flush).

## 10. Completion [DDK/CAP/infer]

Each kick carries 7 TA and 3 3D status updates (`{address, value}`, copied into the shared
block). The TA ones are the client's circular-buffer read offsets and a kick counter
(e.g. `*0xe0019000 = 0x5c` then `0x70`, `*0xe0017000 = 1` then 2); the 3D ones are the
fragment buffers' offsets and a render counter. The EDM writes them when the TA (resp. the
render) is done; the client waits on them before reusing buffer space and on the colour
buffer's sync (write-ops complete) for `glFinish`. With the shim writing them at the kick, the
client never waits.

## 11. Open questions (steps 3 and 4)

1. ~~**Complex-form state**~~ — resolved in "State words (differential captures)" (S.1):
   there is no complex-form state block; the two words after each index list are its vertex
   task, and the "type-3 block" is the triangle's vertex task, not a terminate.
2. **MTE / ISP state words** — mostly resolved (S.2–S.5): presence word, the three ISP
   words, pixel PDS pointers (the §9.3 inference holds), region clip, viewport, culling.
   Still open: the output-select and coordinate words, the rest of the MTE control word,
   ISP word 1 bit 12, the high bits of the pixel PDS size word, two-sided stencil (presence
   bits 3–5), the pass type of the scissor mask draws.
3. ~~**PBE words**~~ — resolved (S.7), as in the transfer queue: rectangle, `COUNT`, stride
   in pixel pairs, address; sideband pack mode 3 for RGB565, 0 for ARGB8888, dither bit 10.
4. **Background object** — layout resolved (S.8): the transfer queue's with one TSP layer, a
   full-surface rectangle whose primary program reloads the colour buffer through the
   texture unit. Open: when the EDM enables it (`ISPBgObj` bit 8), and the texture words.
5. **3D register bitfields** — `TEScreen`, `MTEScreen`, `TEPSG` bit 25 and the ZLS updates
   are pinned (S.6); no other TA or 3D register moved in 66 variations, so `TEAA`,
   `MTECtrl`, `ISPIPFMisc`, `TSPConfig`, `PixelBE`, … need the EDM's register writes (spec
   §13.6) or other variations (multisampling, depth formats, textures).
6. **PB initialisation**: who builds the DPM page table and free list (the descriptor's
   init-page-table flag is clear at the first kick), and the threshold semantics.
7. **The EDM's TA and 3D paths** (`edm.ta` at `0x11d`): which command fields it loads into
   which registers, to confirm the layouts above against the microkernel.
8. **Minimal job for step 4**: drop the transfer context, use one RT data, no secondary
   programs (constant colour in the primary pixel program), our own PDS/USSE programs from
   `usse-asm`, and a kernel-built `SGXMKIF_CMDTA` with one TA kick that also terminates the
   scene.

## State words (differential captures)

Method. `tri` takes options that change one piece of GL state at a time
(`harness/ukernel-extract/triopts.h`); `variations3d.txt` lists 66 runs, captured with
`capture3d.sh` (README "Differential captures", manifest in `extracted/gles2_tri/`).
`state3d.py` names every state-carrying word of both kicks under a stable path and
`diff3d.py` compares each run with `base`, hiding words that only point somewhere else in a
moved object. `base2` (a second identical run) extracts to exactly the same words. In this
section **[CAP `x`]** means "the variation `x` (option `x` of `tri`) flips it"; `size=*`,
`depth=*` … stand for the whole family. The field names are ours unless tagged [DDK]. Where
a field boundary was first suggested by the [PSP2] headers (the presence-word order, the
`doutd` word, the vertex-task words), it is listed only with the capture that confirms it.
Decoders and tests: `state3d.py` (`DECODERS`, `decode_*`), `kick3d.decode_vertex_pds`.

### S.1 The VDM stream, corrected

There is no complex-form state block in any capture. The two words that §9.1 read as a
"complex, last task" state after each index list, and the "type 3" block at word 16 of
kick 0, are the **vertex task of the index list**: an index list block is the header, the
index base, the optional third and fourth words (present bits 22 and 23: `0xf0000000` and
`0x003fffff` in every capture), then two vertex-task words **[CAP]**. Kick 0 goes on after
the triangle's vertex task with a no-op secondary state, the end-of-scene state (S.4) and
the real terminate at word 22; kick 1 repeats those five words.

| word | bits | field | evidence |
|---|---|---|---|
| 1 | 31:28 | partition size **[infer]** | 7: screen-space draws; 15: compiled shaders |
| 1 | 27:0 | PDS vertex program address >> 4 | data size below fits every program |
| 2 | 31:24 | output vertex size, 4-dword units | 1 → 2 **[CAP `varying`, `prim=points`]** |
| 2 | 23:22 | 3 in every capture | |
| 2 | 14:7 | USE attribute size, 16-byte rows | 1 → 2 **[CAP `varying`]** |
| 2 | 6:0 | PDS data size, 16-byte rows | 2 → 3 **[CAP `varying`]** (code starts there) |

The vertex PDS program DMAs each attribute of one vertex with `doutd` from the vertex buffer
(base + vertex index × stride, `movsa` adding `ir0 × stride`); the second attribute of
`varying` lands at attribute offset 4 **[CAP]**. The index list header's primitive type
(29:26) is 0 triangles, 1 lines, 2 points, 3 strip, 4 fan, and 21:0 the vertex count
**[CAP `prim=*`]**; the driver turns a line strip into a line list. `prim=two` only changes
the count. Plain state blocks never set the complex bit (28); their second word decodes as
in §9.1.

### S.2 MTE state blocks

A state program `doutd`s a block from the PDS vertex heap into USSE attributes and starts a
USSE task that copies them to the outputs and `emitmtest`s them (§9.2). `doutd`'s second
word is burst size − 1 (3:0), lines − 1 (7:4), the destination attribute offset (19:8) and
stride − 1 (29:22) **[CAP]**: the clear's `0x02c0000b` copies 12 dwords, the triangle's
`0x02000018` 2 × 9 = 18, which are the lengths of the USSE copy loops; a 19-word stencil
block takes two bursts (16 + 3). The end-of-scene program builds its two-word block with
`douta` instead (value, then the attribute offset in 19:8).

The block starts with a **presence word**; every set bit adds its words, in bit order
**[CAP]**: the clear's `0xd4c3` is 12 words, the triangle's `0xdf43` 18, stencil adds bit 2
and one word, a scissor bit 7 and two.

| bit | words | name in `state3d` | content |
|---|---|---|---|
| 0 | 1 | `isp0` | ISP word 0 (S.3) |
| 1 | 1 | `isp1` | ISP word 1: colour mask (S.3) |
| 2 | 1 | `isp2` | ISP word 2: stencil (S.3) **[CAP `stencil=*`]** |
| 6 | 3 | `pds_sec`, `pds_size`, `pds_pri` | pixel programs (S.5) |
| 7 | 2 | `clip0`, `clip1` | region clip (S.4) **[CAP `scissor=*`]** |
| 8 | 6 | `vp0`…`vp5` | viewport (S.4) |
| 9 | 1 | `wrap` | 0 in every capture |
| 10 | 1 | `outsel` | output selects (S.4) |
| 11 | 1 | `wclamp` | `0x3727c5ac` (1e-5) in every capture |
| 12 | 1 | `mtectl` | MTE control: culling (S.4) |
| 13 | 1 | `term` | end of scene (S.4) |
| 14, 15 | 1, 1 | `coordsize`, `coordfmt` | iterated coordinate sets (S.4) |

Bits 3–5 (back-face copies of the ISP words for two-sided stencil **[infer]**) and 16 and up
never appear. Blocks seen: the clear `0xd4c3`; a draw `0xdf43`, `0xdf47` with stencil,
`0xdfc3` with a scissor; the scissor mask draws `0xd485`; the end of scene `0x2000`.

### S.3 ISP words: depth, stencil, colour mask, blending

**ISP word 0** (`isp0`; base clear and triangle `0x01d00200`):

| bits | field | values | evidence |
|---|---|---|---|
| 7:0 | stencil reference | | **[CAP `stencil=always,85`]** → `0x55` |
| 8 | ISP word 2 present | | **[CAP `stencil=*`]**, with presence bit 2 |
| 9 | ISP word 1 present **[infer]** | 1 in every draw with `isp1` | |
| 17:15 | object type | 0 triangle, 1 line, 3 point | **[CAP `prim=lines`, `prim=points`]** |
| 20 | depth write off | | **[CAP `depthmask=0`]**; set when the depth test is off |
| 21 | colour write off | | **[CAP `mask=0000`]** |
| 24:22 | depth compare | GL order, 0 never … 7 always | **[CAP `depth=*`]**; 7 if off |
| 27:25 | pass type | 0 opaque, 1 blended, 3 scissor mask | **[CAP `blend=*`, `scissor=*`]** |

With the depth test on, the clear's word becomes `0x01c00200` (compare always, writes the
clear depth) and the triangle's `0x00400200` for `less`.

**ISP word 1** (`isp1`): the colour write mask, R G B A in bits 7, 6, 5, 4 **[CAP
`mask=1110`, `mask=1000`]**. Bit 12 is set for every compiled-shader draw and clear for the
clear (`0xf0`); its meaning is open.

**ISP word 2** (`isp2`, stencil) **[CAP `stencil=*`, `stencilmask=0f,f0`,
`stencilop=zero,incr,invert`, `stencilop=decr,incrwrap,decrwrap`]**:

| bits | field |
|---|---|
| 7:0 | write mask |
| 15:8 | compare mask (0 in the clear's word) |
| 18:16 | depth-pass operation |
| 21:19 | depth-fail operation |
| 24:22 | stencil-fail operation |
| 27:25 | stencil compare, GL order |

Operations: 0 keep, 1 zero, 2 replace, 3 increment (saturating), 4 decrement (saturating),
5 invert, 6 increment (wrapping), 7 decrement (wrapping). The clear writes `0x0e0200ff`
(always, replace, write mask `0xff`).

**Blending and colour masks are not fixed-function.** `blend=*` changes only the pass type
and the pixel shader: the compiled program combines its colour with the tile's current
`o0` (`sop2 … o0, pa0, o0`, with the factors and the add or subtract in the instruction);
`mask=1110` / `mask=1000` keep the pass type and end the shader with a byte-masked `sop2wm`
on `o0` besides the ISP write mask **[CAP]**. The fragment colour is a shader constant
(`color=*`): the secondary program DMAs it as f16 values or, for 0/1 components, the shader
builds it from immediates.

### S.4 Region clip, viewport, culling and the other MTE words

**Viewport** (`vp0`…`vp5`, floats): x offset, x scale, y offset, y scale, z offset, z scale
**[CAP `viewport=40,20,16,30`]** → 48, 8, 35, 15 and **[CAP `depthrange=0.25,0.75`]** → z
scale 0.25, offset 0.5. The y scale is positive: framebuffer row 0 is GL's bottom row
(consistent with the region clip below).

**Region clip** (`clip0`, `clip1`): bit 31 of word 0 on; first and last 32-pixel tile column
in word 0 (30:16, 15:0), first and last 16-pixel tile row in word 1 (31:16, 15:0) **[CAP
`size=*`, `scissor=40,20,16,30`]** → `0x80010001`, `0x00010003`. The clear always carries
the whole surface; a draw carries it only when a scissor or viewport is smaller than the
surface.

**Scissor and small viewports** are done with geometry: the driver inserts two ISP-only
draws (presence `0xd485`: no `isp1`, no pixel programs, no viewport; ISP word 0
`0x07e00100`: pass type 3, compare always, no colour or depth write) — a full-surface
rectangle with ISP word 2 = 0, then the scissor rectangle in pixels with ISP word 2 =
`0x02000000` — and then the draw with the region clip of that rectangle **[CAP
`scissor=*`, `viewport=*`]**. **[infer]** they build the ISP's per-pixel mask.

**MTE control** (`mtectl`; `0x01555620` for a draw, `0x40` for the screen-space draws):
bits 1:0 cull, 1 = counter-clockwise, 2 = clockwise triangles in the window coordinates the
viewport produces **[CAP `cull=back` → 2, `cull=front` and `cull=back frontface=cw` → 1;
`frontface=cw` alone changes nothing]**. `cull=both` makes the driver drop the draw. The
other bits never moved.

**End of scene** (`term`, in the kick-1 block `0x2000`): last 32 × 32 block column (31:16)
and row (15:0) **[CAP `size=*`]**: `0x00010001` for 64 × 64, `0x00030001` for 100 × 60.

**Output selects and coordinate words** (open, observations **[CAP]**): `outsel` 19:16 equals
the dwords the vertex task emits per vertex (4 for the triangle, 8 with `varying` and for the
clear, 7 for points, which add a size and two sprite coordinates); bit 8 is set for points;
bits 13:12 are 3 for compiled shaders, 1 (with bit 11) for the clear. `coordsize` /
`coordfmt` are 5 / 1 with `varying`, 5 / 0 for the clear, 2 / 1 for points and 0 / 0
otherwise.

### S.5 Pixel PDS pointers and the size word

The §9.3 inference holds: a pixel PDS pointer (`pds_sec`, `pds_pri`, the special object
words) is the data size in 16-byte rows (31:26) and the program offset from
`PDS_EXEC_BASE` >> 4 (23:0, only 16:0 used) **[CAP]**: in all 66 captures every pointer lands
on a PDSPIXEL program whose code, after that much data, ends in `halt`
(`test_state3d.py`). The size word between them: primary attribute rows (6:0, 1 in every
capture), 3 in 17:16 (the USE task size of the transfer queue's layout), secondary
attribute rows (24:18: 3 for the constant-colour shader, 0 for the clear and `varying`,
whose secondary is a no-op), and 31:25 = 11, 12 or 0 (open) **[CAP `varying`, `color=*`]**.

### S.6 TA and 3D registers

Across all 66 runs only these registers move **[CAP]**:

| register | layout | evidence |
|---|---|---|
| `te_screen` [DDK] | 32 × 16 tiles across − 1 (11:0), down − 1 (23:12) | `size=*` |
| `mte_screen` [DDK] | width − 1 (15:0), height − 1 (31:16) | `size=*` |
| `te_psg` [DDK] | bit 25: render kick with a depth/stencil buffer | `depth=*` |
| `render_flags` | depth + stencil buffer (`0x580`) | `depth=*`, `stencil=*` |

With a depth or stencil buffer the render kick carries six **3D register updates**
(`num_3d_regs`, then `{address, value}` pairs whose address is a word of the render details,
so the EDM patches them there): `ISPZLSCtl = 0x0017100c`, `BIFZLSReqBase = 0x08000000` (the
GENERAL heap), `ISPZLoadBase` = `ISPZStoreBase` = the depth buffer's offset from it, and the
stencil load/store bases = bit 31 | the stencil buffer's offset **[CAP `depth=*`]**. Without
them the render details keep the stencil bases at `0x80000000` and the rest 0. Every other TA
and 3D register in the command and the render details (`TEAA`, `TEMTile*`, `MTECtrl`,
`MTEMSCtrl`, `PixelBE`, `ISPIPFMisc`, `3DAAMode`, `TSPConfig`, `ISPBgObj*`, …) is the same
in every run, pixel format and size included.

### S.7 PBE words

The end-of-tile program's four words and its `emitpix2` sideband have the transfer queue's
layout (`sgx545_transfer.md` §4.2.5) **[CAP `size=*`, `format=8888`, `dither=0`]**:

| word | value | evidence |
|---|---|---|
| 0 | `x0 \| y0 << 16` = 0 | |
| 1 | `(W − 1) \| (H − 1) << 16` | `size=100x60` → `0x003b0063` |
| 2 | `COUNT` `0x80` (15:8), stride in pixel pairs − 1 (27:16) | 64 → 31, 100 → 51 |
| 3 | colour buffer address | |
| sideband | pack mode (5:0), tile relative (9), dither (10) | see below |

The stride field counts pixel pairs for both formats (a 100-pixel surface has a 104-pixel
stride, 51); the sideband pack mode is 3 for RGB565 and 0 for ARGB8888, and `dither=0`
clears bit 10.

### S.8 Background object

The background object (`bg_obj_base_dev_addr`, 0x200 bytes) has the transfer queue's layout
(`sgx545_transfer.md` §4.2.3) with one TSP layer **[CAP]**: words 0–2 are the PDS pointers,
0 in the buffer and patched at render time (the special object words of the command hold
them, and the `hw_bg_obj_prim_pds_update_list_dev_addr` list holds the primary pointer
`0x0c00040e`); words 3–8 the texture coordinates (0, 0), (1, 0), (0, 1); word 9 zero; word 10
the vertex format `0x202` (one layer); words 15–22 the vertices (0, 0), (W, 0), (0, H) with
z = 1.0 in the 24.8 fixed-point format **[CAP `size=*`]**. `ISPBgObjTag = 0x02046400` (two
TSP dwords per vertex, the object at `BIF3DReqBase + 0x464000`), `ISPBgObjDepth` = 1.0 and
`ISPBgObj = 0x300` never change. Its primary program (`0xe40040e0`) starts the plain copy
shader (`o0 = pa0`) with an iterated coordinate (`douti`) and a texture fetch (`doutt`)
whose state holds the colour buffer address, `(W − 1) << 12 | (H − 1)` with a format byte
(`0xc5` RGB565, `0xcc` ARGB8888) and a stride-dependent word **[CAP `size=*`,
`format=8888`]**: the background object **reloads the previous colour buffer**. `glClear`
is not the background object: it is a screen-space triangle (0, 0), (2W, 0), (0, 2H) with
z = the clear depth and the colour packed as `0xAARRGGBB` in each vertex **[CAP `clear=*`,
`cleardepth=0.5`, `size=*`]**, and `noclear` simply leaves it out.

### S.9 What a minimal job needs, and what stays open

For one opaque, unclipped triangle the state is now fully determined: a state block with
presence `0xdf43` (ISP word 0 `0x01d00200`, ISP word 1 `0x10f0`, the two pixel pointers and
the size word, the viewport, `outsel`, `wclamp`, `mtectl`), the index list with its vertex
task, the end-of-scene block with `term`, the TEScreen/MTEScreen pair and the PBE words for
the surface. Open: the output-select and coordinate words beyond the observations above, the
rest of `mtectl`, ISP word 1 bit 12, the high bits of the pixel size word, the pass type 3
draws, two-sided stencil, the ZLS control word (no depth format variation yet), the
background reload's texture words and when the EDM runs that object.
